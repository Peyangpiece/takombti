## 0. この文書について

### 0.1 目的

本人ではなく**友達が本人について答える**アンケート（他己診断）を集め、指定した人数が答え終わった時点で、
4 つの軸による 16 タイプのどれに見られているかを判定し、詳しく面白い分析文を表示するウェブアプリを作る。
この文書は、作る人がこれだけを読めば迷わず実装・テストできることを目標にする。

### 0.2 用語

| 用語          | 意味                                                               |
| ------------- | ------------------------------------------------------------------ |
| ホスト        | 診断を作り、自分について友達に答えてもらう人                       |
| 回答者        | ホストに頼まれて、ホストについて答える友達                         |
| 診断          | ホストが 1 回作る 1 件のアンケート。人数・回答・結果をまとめたもの |
| 目標人数（N） | ホストが作るときに決める回答者の人数                               |
| 軸            | 性格を分ける 4 つの物差し（後述）                                  |
| 極            | 軸の両端（例：外向と内向）                                         |
| 自己回答      | ホストが自分で同じ質問に答えたもの（任意）                         |

### 0.3 前提と、そう決めた理由

| 前提                                                                       | 理由                                                                                                                                                                                                                                                       |
| -------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 4 軸・16 タイプの枠組みは MBTI を参考にする                                | 依頼の条件。若い世代に広く知られ、説明なしで楽しめる                                                                                                                                                                                                       |
| 製品名・画面に「MBTI」を使わない。16Personalities のタイプ名・絵も使わない | MBTI® は Myers & Briggs Foundation の登録商標（出版は The Myers-Briggs Company、日本では日本MBTI協会が普及を担う）。16Personalities のタイプ名や絵は NERIS Analytics の著作物。自前の名前と絵にすれば権利の心配がない（公開前に専門家へ最終確認する。§13） |
| 4 文字の記号（例：ENFP）をタイプ名と並べてはっきり出す                     | 既存の診断と照らし合わせて楽しめ、シェアもしやすい。記号の並びそのものは一般に広く使われている。権利の最終確認は §13 C1 で行う                                                                                                                             |
| 分析文は**決まった規則で組み立てる**（生成 AI を使わない）                 | 文のすべてを回答データにさかのぼって説明でき、「正しい」ことを保証できる。費用もかからず、同じ回答なら必ず同じ結果になる                                                                                                                                   |
| 娯楽として提供し、心理検査とはうたわない                                   | MBTI 型の分類は、再検査で型が変わりやすいなど信頼性に議論がある。誤解を招かないよう、画面に注記を出す（§9.2）                                                                                                                                              |

### 0.4 他己診断で測れること・測れないこと（設計の根拠）

性格心理学の研究では、他人による評定は本人の評定と同じくらい性格をよく言い当てることがあり、
特に**外から見えやすい特性（人と話す量など）ほど本人と他人の評価がよく一致する**ことが知られている
（Funder の「現実的正確さモデル」、Vazire の「自己と他者の知識の非対称性（SOKA）モデル」など）。
逆に、心の中の不安など見えにくいものは他人には当てにくい。

このため本アプリでは次の方針を取る。

- 質問はすべて**友達が実際に見聞きできる行動**で書く（「〜と感じている」ではなく「〜している」）
- 判定結果は「あなたの本当の性格」ではなく「**周りからこう見えている**」と表現する
- 自己回答があれば、自分の見方とのずれを「ギャップ」として示す（ジョハリの窓の「自分は知らないが他人は知っている自分」に当たる部分で、他己診断ならではの面白さになる）

### 0.5 名前

- 名前：**たこ診**（たこしん）。表記はひらがなの「たこ」＋漢字の「診」で固定する
- 副題：**友達が答える16タイプ診断**。「他己（たこ）」の読みに気づかない人もいるため、トップ・シェア画像・リンクの見出し（OGP）では名前と必ずセットで出す
- 由来：「他己（たこ）診断」の略
- 看板のキャラクター：タコ（自前で描く）。界隈の色に合わせた 4 色の姿を用意し、結果画面とシェア画像に出す
- 公開前に、商標（特許庁の J-PlatPat）、アプリストア、ドメインで同じ・似た名前がないかを調べる（§13 C1）

ほかの候補だったもの（ウワサの16・みられ16・トモタイプ・ヒトミル）は使わない。

## 1. 全体の流れ

```
ホスト                          回答者（N 人）
───────                        ─────────
① 名前と人数 N を入れて作る
② （任意）自分でも答える
③ 招待リンクを LINE などで送る ──→ ④ リンクを開く
                                  ⑤ 16〜32 問に答える（約 3〜6 分）
⑥ 回答状況を見る（○/N 人）  ←── ⑤ を N 人が終える
   ※ N 人そろうまで結果は一切見えない
⑦ N 人目が答えた瞬間に結果が確定
⑧ 結果発表 → 詳しい分析 → シェア
```

要点：**結果は N 人目の回答が保存された時点で 1 回だけ計算し、以後は変えない**。
それより前は、途中の傾向も含めて、サーバーの外に結果に関わる情報を一切出さない。

## 2. 16 タイプの枠組み

### 2.1 4 つの軸

MBTI の 4 つの二分法（エネルギーの向き・ものの見方・判断のしかた・外の世界への接し方）にならい、
他人から見える言葉に言い換える。

| 軸            | 記号  | 左の極                       | 右の極                       | 他人から見える違い                                 |
| ------------- | ----- | ---------------------------- | ---------------------------- | -------------------------------------------------- |
| A1 エネルギー | E / I | **外向** E「ワイワイ充電」   | **内向** I「ひとり充電」     | 人と過ごして元気になるか、一人の時間で元気になるか |
| A2 ものの見方 | S / N | **現実** S「目の前のリアル」 | **直観** N「頭の中の可能性」 | 具体的な事実を話すか、想像・アイデアを話すか       |
| A3 判断       | T / F | **思考** T「ロジック優先」   | **感情** F「気持ち優先」     | 理屈と効率で決めるか、人の気持ちを大事に決めるか   |
| A4 接し方     | J / P | **計画** J「きっちり段取り」 | **柔軟** P「その場のノリ」   | 前もって決めて動くか、成り行きに合わせて動くか     |

### 2.2 4 つのグループ（「界隈」）

16 タイプを 4 つにまとめる。まとめ方は、MBTI 系の診断で一般的な「NT・NF・SJ・SP」の組み合わせに従う
（2 文字目が N のときは 3 文字目、S のときは 4 文字目で分ける）。
名前は、いまの若い世代に通じる「〜界隈」という言い方で付ける。

| グループ | 条件     | 名前             | ひとこと                                       | 飾りの色 ／ 文字・背景の濃い色 ／ 暗い背景での文字色 |
| -------- | -------- | ---------------- | ---------------------------------------------- | ---------------------------------------------------- |
| G1       | N かつ T | **考察界隈**     | 頭の中がいつもフル回転。仕組みと可能性が大好物 | 藍 `#4C6FFF` ／ `#3B5BDB` ／ `#7D95FF`               |
| G2       | N かつ F | **エモ界隈**     | 心の動きに敏感。人と意味を大事にする           | 桃 `#FF5FA2` ／ `#C2255C` ／ `#FF5FA2`               |

## 3. 質問

### 3.1 作り方の決まり

1. 質問は **32 問**（1 つの軸に 8 問）。そのうち、一人が答えるのは **16〜32 問**（§3.5）。基本の 16 問で約 3 分、深掘りが入った 32 問で約 6 分（目安は「約 3〜6 分」と出す）
2. 各軸 8 問は、**基本 4 問**（全員が答える）と**深掘り 4 問**（必要な人だけ）。どちらも**左の極向き 2 問・右の極向き 2 問**。「なんでも『そう思う』と答えてしまう癖」（黙従傾向）が結果を一方に寄せないようにするため
3. 友達が**見聞きできる行動**で書く（§0.4）。深掘りの問は、基本の問より具体的な場面で聞く
4. 主語は `{name}`（ホストが付けた呼び名）。「{name}は」で始めて自然に読めるようにする
5. 軸が続けて並ばないよう、A1→A2→A3→A4 を繰り返す順で出す。並び順は全員同じにする（順番による偏りを人によって変えないため）
6. 「〜しない」のような打ち消しの文は使わない（読み違いが増えるため）
7. 最初に選んだ関係（§3.6）に合わせて、その関係で見られる場面の言い方に差し替える。意味（どの極の行動か）は変えない

### 3.3 自己回答用の言い換え

同じ 32 問を、主語を「わたし」に、文末を自分のことに合う形に直したものを使う。場面の差し替えはしない（自分のことなので、ふだんの文で聞く）。
意味を変えないこと。例：

- Q1「わたしは、初対面の人がいても自分から話しかけにいく」
- Q2「わたしは、大人数で過ごしたあと、ひとりの時間がほしくなる」
- Q18「わたしは、相談されると、まず相手の気持ちに共感する」

32 問すべての自己回答版は、データファイル（§11.4 `src/data/questions.ts` の `selfText`）に持たせる。

### 3.4 答え方

- 7 段階：「ちがう」←●●●○●●●→「そう」。左から 1〜7 の値を持つ。真ん中（4）は「どちらとも」と、丸の下にも小さく書く。真ん中の丸の色も、背景との明るさの差を 3:1 以上にする
- 加えて「**わからない**」を選べる（友達が見たことのない行動もあるため。例：部屋の様子）。自己回答では選べない
- 1 つの軸で、1〜7 で答えた問が 3 問未満だと、その軸を判定できない。送信の前にその軸の問へ戻るよう案内する（§5.3）

### 3.5 答えによって出す問を変える（深掘り）

1. まず基本の 16 問に答えてもらう
2. 基本の 16 問に答え終わったら、軸ごとに、基本の問だけで次を確かめる
   - 1〜7 で答えた基本の問が 3 問未満（「わからない」が多い）
   - または、1 問あたりの点（§6.1 の `s`）の平均が −1 より大きく +1 より小さい（＝合計の絶対値が答えた問の数より小さい。半々に近い）
3. どちらかに当たる軸だけ、その軸の深掘り 4 問を後ろに足す。足す順は §3.2 の深掘りの表の順
4. ハッキリした人は 16 問、全部の軸が半々に近い人は 32 問になる。足した問の数は画面で知らせる（§4.8）
5. 前の問に戻って基本の答えを変えたら、もう一度 2 を確かめ直す。出さなくなった深掘りの問の答えは送らない
6. サーバーでも同じ決まりで確かめ、出すべき深掘りの問が抜けている回答や、出していない問に答えている回答は受け付けない（§5.3）
7. 送る形：32 問ぶんの値を番号順に並べる。1〜7 は答え、0 は「わからない」、−1 は出していない問

理由：半々に近い軸ほど、問を増やすと結果が安定する。ハッキリした軸に同じ数の問を重ねても結果はほとんど変わらないので、答える人の手間を減らす。

管理用の画面は `hostKey` を URL の `#` より後ろに置く。`#` より後ろはブラウザがサーバーに送らないので、サーバーやホスティングの記録（ログ）にも、リンク元の情報（Referer）にも残らない。

### 4.2 S1 トップ

- 大きな見出し：「友達が答える、あなたの 16 タイプ」
- 小見出し：「自分で答える診断とはちがう、"周りから見たあなた"がわかる」
- ボタン 1 つ：「診断をつくる（無料・登録なし）」
- 下に 3 枚の説明カード：①人数を決めてリンクを送る ②友達が 3〜6 分で答える ③全員そろったら結果発表
- 4 つの界隈を色付きで紹介（タップで各界隈の 4 タイプを表示）
- この端末で作った診断があれば、「つくった診断」として一覧で出す（§8.3）。人数をふやす入口は回答状況と結果の画面にあるので、ここには置かない（作った診断が増えるほどトップが長くならないように）。それぞれに今の状態の札（「結果が出ました」「あと N 人」「期限切れ」「見つかりません」）を付ける
- **結果の見本**：架空の結果（「見本：たろうは友達 5 人から見ると」）で、タイプ・4 軸メーター・データでわかるあなたの文を 2 つ見せる（16 タイプの紹介（§4.14）への案内は、すぐ下の「4 つの界隈・16 タイプ」の 1 か所だけにする。同じ行き先のボタンを 2 つ置くと迷うため）。友達に頼む前に、どんな結果が出るかを分かってもらうため。文は結果の画面と同じ組み立て方で作る
- **管理用リンクから開く**：管理用リンクを貼り付けて、別の端末やホーム画面のアプリで診断を開く。ふだんはページの下にたたんで置き、ホーム画面のアプリで開いていて「つくった診断」がまだないときだけ、上のほうに開いて置く（iPhone のホーム画面のアプリは Safari と保存場所が分かれているため。§11.10）
- 「全員そろった」の通知を押して開いたとき（`/?open={surveyId}`）は、端末に覚えてある管理用の鍵でその診断を開く

### 4.3 S2 診断を作る

1 画面に 2 項目だけ。入力が少ないほど作る人が増えるため。

1. **呼び名**（必須、1〜12 文字）
   - 見本：「たろう」「はなちゃん」
   - 質問文に「{name}は、…」と入るので、その見本を入力欄の下にリアルタイムで表示する
2. **何人に答えてもらう？**（必須、3〜30 人、初期値 3）
   - 初期値は、回答が集まらずに結果まで届かない診断を減らすため、いちばん少ない 3 人にする（すでにある診断の人数は変えない）
   - 「−」「＋」ボタンと大きな数字。長押しで連続して変わる
   - 下に「まずは、確実に答えてくれる 3 人がおすすめ。人数がそろうまで結果は見られません」と出す

- 作成画面のアドレスの `?entry=`（`thanks`・`public`・`top`・`types`）で、どこから作成画面に来たかを受け取り、計測に使う（§11.11）

ボタン：「つくる」。押すと診断ができ、S4 の招待リンクの共有へ進む（送る気持ちがいちばん強いのは作った直後なので、自己回答より先にする）。ボタンは画面の下に固定し、「つくると、利用規約とプライバシーポリシーに同意したことになります」の文もボタンのすぐ上にいっしょに固定する（文が隠れたまま押せないように。答える画面 R1 の「はじめる」も同じ）。

**作ったあとは、人数をふやせるが、へらせない**（§5.4）。依頼の条件「指定した人数が答え終わってから結果を出す」を守るため、
減らして早く結果を見ることはできないようにする。作る前の確認ダイアログでこの点を伝える。

### 4.4 S3 自己回答（任意）

- 入り口：S4 の「待っている間に、自分でも答えておく？」と、S5 の「自己回答をする」。どちらも見落とされないよう上のほうに置く（S4 は説明の文の「待っている間に、自己回答もできます」のリンクと、招待の欄のすぐ下の欄。S5 は「もう一度リンクを送る」のすぐ下で、スマホの 1 画面目に入るように）。作った直後には出さない（先に招待リンクを送ってもらうため）
- 冒頭：「自分でも答えておく？」「自分が思う自分」と「周りから見た自分」のギャップがわかる
- 「16〜32 問」と添える（時間の目安はボタンに出す）
- ボタン：「答える（約 3〜6 分）」「答えずに戻る」（自己回答を保存済みなら「答え直す（約 3〜6 分）」「このままにする」）。答えずに戻っても、結果が出るまではあとから答えられると書く。答え終えたとき・戻るときは S5 へ
- 質問の画面は R2 と同じ部品を使い、文だけ自己回答版にする。「わからない」は出さない（自分のことなので）
- 自己回答は**結果が確定するまで**いつでも出し直せる。確定した後は変えられない。一度結果を見たあと（人数をふやして受付に戻したとき）も、答えられない（結果に引きずられて、ギャップが正しく出ないため。`HostView.selfOpen`）
  （結果を見てから答えると、結果に引きずられてギャップが正しく出ないため）

### 4.5 S4 招待リンクの共有

- 招待リンク（`/a/{surveyId}`）を大きく表示
- ボタン：「LINE で送る」（LINE の共有 URL）、「文章＋リンクをコピー」「リンクだけコピー」、「ほかのアプリで送る」（端末の共有機能 `navigator.share`。使えるときだけ）、「QR コードを出す」
  - 「LINE で送る」：スマホは LINE アプリの送信先の選択を開く。パソコンは、PC 版 LINE のアプリを文つきで開く方法を LINE が用意していないので、文とリンクをコピーして PC 版 LINE のトークに貼り付けてもらい、ブラウザの LINE で送るリンクも出す
- 送る文（LINE・文章＋リンクのコピー・ほかのアプリで送る、で共通）：「私って周りからどう見えてるか知りたいので、答えてほしい！ 約3〜6分・登録なし。1人ずつの答えは私には表示されません。{N}人そろったら結果が出るので、出たら見せるね。」＋改行＋招待リンク
  - 友達が安心して答えられるよう、何のための診断か・かかる時間・登録なし・だれが何と答えたかは作った人に見えないこと・何人そろったら結果が出るかを入れる。「完全匿名」など、実装より強い言い方はしない
  - {N} は実際の人数。もう答えてくれた人がいるとき（送り直し）は、先頭に「もう答えてくれた人はありがとう！ まだの人は、」を入れる
  - かかる時間は `ANSWER_TIME_LABEL`（`src/data/questions.ts`）。回答にかかった時間の計測（§11.11）を見て見直し、裏付けなく短くしない
  - 画面には「送る文の見本」として、この文とリンクを出す。リンクには送り方の目印（`?from=`）を付ける。管理用のリンクは入れない
  - 送るのはホスト自身。自動で送ったり、催促したりはしない（作る側の決まりで、画面には書かない）。端末の共有を閉じても（キャンセルしても）診断には何も起きない
- 自己回答がまだで受付中なら、招待の欄のすぐ下（管理用リンクの保存の上）に「待っている間に、自分でも答えておく？」の欄と「自己回答をする（約 3〜6 分）」のボタンを出す
- 注意書き：**管理用のリンク**（`/h#{hostKey}`）は自分だけのもの。なくすと結果を見られないので、「自分の LINE に送る」「管理用リンクをコピー」のボタンで保存をすすめる。友達に送るリンクの「コピー」と取り違えないよう、名前を長めにして横に並べず、保存のボタンが隠れないよう、この画面では下に固定するボタンを使わない

### 4.6 S5 回答状況

- 大きな表示：「3 / 5 人 回答ずみ」と、人数分の丸（答えた人の分だけ色が付く）
- 丸は答えた順に色が付くだけで、だれが答えたかは出さない
- そろうまで、**結果につながる情報は一切出さない**（途中の割合・傾向も出さない）
- あと何人かを言葉でも出す：「あと 2 人で結果発表！」
- ボタン：「もう一度リンクを送る」、そのすぐ下に自己回答（まだなら説明つきの欄「待っている間に、自分でも答えておく？」、答えたあとは「自己回答を直す」）。通知の欄はその下
- **そろったら通知で知らせる**（§11.10）：「通知を受け取る」を押した端末に、全員が答えたとき 1 回だけ通知する。端末に「オン」と覚えていても、開くたびにサーバーの登録を確かめ（`POST /api/host/push/status`）、消えていれば「オフ」に戻す（結果が出て通知を送ったあと、人数をふやして受付を再開したときなど）。メール・電話番号は集めない。通知を止めている端末には、設定で許可すると使えると書く。iPhone・iPad の Safari で開いているときは、ホーム画面に追加する手順（管理用リンクをコピー →「ホーム画面に追加」→ ホーム画面のたこ診で「管理用リンクから開く」に貼り付け →「通知を受け取る」）と「管理用リンクをコピー」のボタンを出す。手順は長いので「iPhone で通知を受け取る方法」の中にたたんでおく。通知に対応していないブラウザでは欄を出さない
- 10 秒ごとに状況を取り直す（画面が見えているときだけ。§11.3）
- 人数がそろったら、画面全体で「そろった！」の演出 → 「結果を見る」ボタン

### 4.7 R1 回答のはじめ

- 「**{name}** について答えてください」
- 「約 3〜6 分・16〜32 問・匿名。{name} には、1 人ずつの答えは表示されず、みんなの答えをまとめた結果だけが届きます」（「見えません」とは書かない。ホストが友達のふりをして何人分も答えると、ほかの人の答えの一部を推測できてしまい、仕組みでは防ぎきれないため。§8.4）（招待リンクを貼ったときの説明文も同じ時間）
- 「答えによって、次の質問が変わります」「見たことのない行動は『わからない』を選べます」
- ボタン：「はじめる」→ 関係を選ぶ画面（§3.6）→ 質問
- 締め切り済み・期限切れなら E1 を出す

### 4.8 R2 質問（いちばん大事な画面）

**1 画面に 1 問**。考える量を減らし、指一本で進められるようにする。

```
┌────────────────────────┐
│ ←      7 / 16      ━━━━──── │  ← 戻る・番号・進み具合の帯
│                              │
│  たろうは、                   │
│  その場のノリで予定を          │  ← 質問文（大きめ・2〜3 行）
│  変えても平気だ                │
│                              │
│  ちがう ●  ●  ●  ○  ●  ●  ● そう │  ← 7 つの丸。両端ほど大きい
│                              │
│        わからない              │  ← 文字だけの控えめなボタン
└────────────────────────┘
```

- 丸の大きさ：両端 52px、内側に行くほど小さく（44px・38px）、真ん中 30px。どれも押せる範囲は 44px 以上（§10.2）
- 色：左側は灰がかった色、右側は診断のテーマ色。真ん中は中間の灰色（背景との明るさの差 3:1 以上。§3.4）
- 丸を押すと、**0.25 秒後に自動で次の問へ**。軽く震わせ（対応端末のみ）、押した丸が一瞬ふくらむ
- 左右のスワイプでも前後の問へ動ける。戻ったときは前の答えが選ばれた状態で出る
- 番号の分母は、そのときに出すと決まっている問の数（最初は 16）。深掘りの問を足したときは分母が増え、「もう少しだけ！ あと 4 問」のように足した数を知らせる
- 深掘りの問が入ったときは、番号の横に残りの目安時間を出す（「あと 2 分ほど」。1 問 11 秒で数え、45 秒未満は「もうすぐ終わり」）。基本の問だけなら約 3 分なので、途中でやめる人を減らすため。基本の 16 問だけのときは出さない
- 基本の問の 4 問ごとに短いひとこと（例：「いいペース！」「あと半分！」「ラスト 4 問！」）を出す
- 途中で閉じても、同じ端末で開き直せば続きから（答えはその端末の中だけに保存。§8.3）

### 4.9 R2 の最後：確認と送信

- すべての問のあと、「これで全部です」の画面。「質問にもどる」で戻れる
- 判定できない軸があれば、その軸の「わからない」の問へ案内する（§3.4）
- 送信ボタン：「送る」
- 送信中は二度押しできないようにする

### 4.10 R3 回答完了

- 並び（回答を受け付けたあとにだけ出す）：1. お礼「ありがとう！ 回答を受け取りました」 2. 自分の回答だけから見たタイプ 3. みんなの答えを合わせた結果とはちがうことの説明 4. 「次は、あなたが周りからどう見えているか聞いてみる？」 5. 「自分の診断をつくる」
- 「{name} の結果は、{N} 人そろったら {name} だけが見られます」
- あと何人で結果が出るかを表示：「あと 2 人」（人数だけ。中身は出さない）
- **あなたの答えから見ると**：答えた人自身の答えだけから出したタイプ（4 文字・タイプ名・タコ）を「{name} は ○○（XXXX）寄り」と見せる。端末の中だけで計算し、送らない。ちょうど 0 の軸は右の極（§7.6 と同じ）で、そういう軸があれば「どちらとも言えない軸が N つあります。そこは決まらないので、仮に片方の文字で出しています」と添える（全問「どちらとも」でもタイプが出るので、言い切って見えないように）。「これはあなたの答えだけから見たタイプです」と添える（全員の結果がホストだけに見えることは、画面の上で伝えているので繰り返さない）
- 誘導：「次は、あなたが周りからどう見えているか聞いてみる？」→「自分の診断をつくる」（`/new?entry=thanks`。はじめの人数は 3 人）。相手の呼び名や回答は新しい診断に引き継がない。ポップアップや作成の強制はせず、作らない人は何もしなくてよい
- 回答者に、そのホストの結果は見せない（ホストが公開した場合は S7 で見られる）

### 4.11 S6 結果発表

開くとまず演出（2〜3 秒、飛ばせる）：

1. 画面が暗くなり「{N} 人の答えを集計中…」
2. 4 つの軸の文字が 1 つずつ回転して止まる（E→N→F→P のように）
3. 界隈の色が広がり、4 文字とタイプ名が出る

続いて下に長く読める分析（中身は §7）。上から順に：

1. タイプのカード（4 文字・界隈・タイプ名・キャッチ・タグ）
2. 4 軸メーター
3. 友達から見たあなた（本文）
4. 強み／ちょっと気をつけたいところ
5. データでわかるあなた（回答の数字から作る文）
6. （欠番。自己回答があるときは、2 の 4 軸メーターを「周りと自分の比較」に置きかえる）
7. 関係ごとの見え方（条件を満たすとき）
8. 相性のいいタイプ（遊び）
9. シェア
10. 応援のお願い（行き先＝特典つきの応援か、特典なしの応援 `NEXT_PUBLIC_SUPPORT_URL` の、どちらかがあるときだけ）

折りたたみ：5〜8 は見出しを押すと開く形にして、最初の画面が長くなりすぎないようにする。5（データでわかるあなた）は、はじめから開いておく。

**応援のお願い**：結果という価値を先に受け取ってもらい、最後に、そのお返しとして応援をお願いする（返報性）。2 段に分ける：

1. まず特典なしで応援をお願いする（「応援する」「今回は閉じる」）。特典のことはここでは出さない
2. 「応援する」を押すと、同じ場所が「応援しようとしてくれた、やさしいタコさんへ」に切りかわる。その場で、お礼に**スペシャルなシェア画像**を贈る（無料。`surveys.gift_at`。その場で作れ、シェアの欄にも出る）。さらに、支払ってくれたらお礼に**くわしい分析**を開くと、値段といっしょに案内する（特典つきの応援。Stripe）。特典なしの応援（`NEXT_PUBLIC_SUPPORT_URL`）があれば「特典なしで応援する（好きな金額）」も並べる。この段には「やめる」を置かないが、結果の画面の中に出すだけで画面をふさがないので、そのまま下へ読み進められる

押しつけないための決まり：

- 受け取ったもの（友達 N 人の答えをまとめた結果・無料・広告なし・登録なし）と、お金の使い道（サーバー代と新しい機能づくり）を正直に書く
- 結果のタイプのマスコットから「〇〇のタコより」として出す
- これまでの結果は、応援しなくてもすべて見られると書く。罪悪感をあおる言い方・急がせる言い方・「今だけ」など期間を限る言い方・値引きの見せ方はしない（景品表示法の有利誤認・二重価格のおそれがあるため）
- 有料の特典は、払う前に内容と値段を見せる（特定商取引法）。「プレゼント」と書くのは無料で贈るスペシャルなシェア画像だけで、くわしい分析は「応援が済んだら、お礼に」と書く
- 1 段目の「今回は閉じる」で、その端末では 30 日出さない。回答者の画面・管理の画面には出さない
- どちらの行き先もなければ出さない。特典を開いた診断には出さない

**特典つきの応援（有料）**：支払ってくれたホストに、お礼として、その診断の「くわしい分析」を開く。特典を付けると寄付ではなく販売になるので、特定商取引法に基づく表記（`/legal`）を出し、利用規約に定める（第 4 条の 2）。

- 出すのは、`STRIPE_SECRET_KEY`・`STRIPE_WEBHOOK_SECRET`・`SUPPORT_PRICE_YEN`（50〜10000 円）と、販売者の表示（`src/data/seller.ts`）がそろったときだけ
- 金額は 3 つから選べる。`SUPPORT_PRICE_YEN` がいちばん安い金額で、`SUPPORT_TIERS_YEN`（「300,500,1000」の形）があればその金額、なければ 500 円・1,000 円を足す（いちばん安い金額より高いものだけ。3 つまで）。特典はどの金額でも同じで、そのことを金額のすぐ下と `/legal` に書く
  - 金額は安い順に並べ、はじめは真ん中の金額（300 円が基本なら 500 円）を選んでおく（運営者の判断）。選んでいる金額を、枠に加えて少し大きく見せる（前は選択に関係なく真ん中だけを大きく見せていたが、選んだものが大きくなる形にした）。「おすすめ」などの言葉は使わない。呼び名は「ちょっと応援・しっかり応援・たっぷり応援」
  - 支払いのボタンの前に、条件をまとめて出す（特定商取引法 第12条の6 の最終確認の表示）：代金（税込・1 回だけ）・支払いの時期と方法（「クレジットカード。申し込んだときに支払いが確定します」。`src/lib/premiumTerms.ts` の `PAYMENT_TERMS`）・見られる時期（支払いが済みしだい）・見られる期間（「あと N 日（M月D日まで）見られます」と、その診断の保存期限 `delete_at` までの本当の残り日数を出し、結果が出てから 180 日。診断を消すと見られない）・返金（提供したあとはできない。見られないときは返金）。Stripe の支払いのページにも、支払いの時期と方法・返金・期間を `custom_text.submit` で出す
  - 保存期限までの残り日数（切り上げ。`HostView.daysLeft`）が 7 日（`MIN_PREMIUM_DAYS`）に満たない診断では売らない（支払ってすぐ見られなくなるため）。画面では金額を選ぶところと支払いのボタンを出さず、「保存期限（M月D日）まであと N 日のため、特典つきの応援は受け付けていません」と書く。サーバーも支払いのページを作らない（`/api/host/premium` が `too_late`）
  - 支払いの方法はクレジットカードだけ（`payment_method_types[0]=card`）。コンビニ払いなどのあとで払う方法は、支払いが済む前に開き直されて二重に払われやすいため。`/legal` の支払い方法・支払いの時期も「クレジットカード（Stripe）」「申し込んだとき」にそろえる
  - 支払いの前に「18 歳以上です（18 歳未満の方は、保護者の同意を得ています）」にチェックしてもらう（チェックがないと支払いのボタンを押せない）
  - 支払いのボタンは「◯◯円で特典つきの応援をする」とし、売っていることが分かるようにする。特典の中身は「◯◯タイプに共通の読み物」と「あなたの友達の答えから組み立てた読み解き・データ」を分けて書く
  - 診断を消す確認では、特典があれば「支払った特典も見られなくなります。返金はできません」と出す
  - してはいけないこと：「おすすめ」「いちばん人気」などの直接的な言葉や、本当でない表示、高い金額のほうが特典がよいと思わせる書き方、選んでいない金額で支払いのページを開くこと。2 枚目（カードの裏）の「応援して続きを見る」は、金額を選ぶところへ移るだけにする
  - サーバーは、送られた金額が選べる金額のどれかであることを確かめてから、その金額で支払いのページを作る
  - /admin の「応援のお願い」に、支払いの金額ごとの件数と合計金額（支払った日で分ける。`payments` から数える）を出す
- これまでに応援してくれた人数：応援のお願いの 2 段目、金額を選ぶところのすぐ上に「これまでに 〇 人のタコさんが応援してくれました」と出す（小さなタコを 3 匹並べる）。数は支払いの記録（`payments`）の本当の件数で、全額を返金した・取り消された支払い（`refunded_at` があるもの）は数えない。20 人に届くまでは出さない（「まだ 2 人」と出ると、かえって応援しにくくなるため）。/admin の金額ごとの件数と合計金額も、返金した・取り消された支払いを除く
- サポーターのシール：特典を開いた（支払った）診断は、スペシャルなシェア画像の右上に、少し傾けた丸い金のシール（ハート・「SUPPORTER」・「たこ診を応援」）を入れられる。金額は入れず、どの金額でも同じ。画像を作るところのチェックで外せる（はじめは入れる）。サーバーは、支払った診断のスペシャル版のときだけシールを描く
- 支払いは Stripe の支払いのページ（Checkout）。たこ診が Stripe に渡すのは、どの診断の特典かを示す診断の ID だけ。管理用の鍵は渡さない。戻り先は `/h/thanks` で、支払いの前に端末に覚えた結果の画面へ戻る
- 応援の 2 段目のスペシャルな画像の保存のボタンは、シェアの欄と同じく実際の動きに合わせた名前にする（「縦を保存・共有」／共有の画面がない端末では「縦をダウンロード」）
- 支払いのボタンの下、利用規約、特定商取引法に基づく表記に「18 歳未満の方は、保護者の同意を得てから支払ってください」と書く（未成年が親の同意なく結んだ契約は、原則として取り消せるため。LINE から中高生が使うことも考えられる）
- 同じ診断で支払いのページを開き直すと、前に作ったページを閉じる（Stripe の Checkout Session を expire。`surveys.checkout_session_id` に最後のページを覚える）。2 つのタブで開いた支払いのページの両方で払われないように
  - 閉じられなかったときは、そのページを Stripe に問い合わせる。もう払われていれば（`status: complete` か `payment_status: paid`。知らせが届く前のことがある）新しいページを作らず、`processing` を返して「支払いを確かめています。少し待ってから開き直してください」と出す。期限切れ（`expired`）か、Stripe にない（404。鍵を替えたときなど）なら、新しいページを作る。確かめられないとき（Stripe が応えないなど）も新しいページを作らず、`stripe_error`（502）
  - 2 つのタブでほぼ同時に押されても前のページを閉じてから作る順に並ぶよう、診断の行の鍵（`for update`）を持ったまま Stripe に問い合わせる。その代わり、Stripe への問い合わせは 1 つ 10 秒で打ち切る（`AbortSignal.timeout`）。打ち切った・つながらないときは `stripe_error`（502）を返し、画面は「支払いのページを開けませんでした。もう一度試してください」と出す
- 支払いが済んだことは、Stripe の知らせ（Webhook：`checkout.session.completed`・`checkout.session.async_payment_succeeded`、`/api/stripe/webhook`）の署名を確かめてから信じ、`surveys.premium_at` を付ける。5 分より古い知らせは受け付けない。知らせの中身も確かめる：診断の ID は、たこ診が支払いのページを作るときに入れた `metadata.survey_id` だけを使う（`client_reference_id` は Payment Link などで訪問者が URL に付けられるので使わない）。通貨が円で、払われた金額（`amount_total`）が、支払いのページを作るときにたこ診のサーバーが入れた `metadata.amount_yen` と同じで、50〜10000 円であること（いまの設定にはよらない。あとで金額の設定を変えたり、特典を出すのをやめたりしても、払われた支払いを見落とさないため）。`amount_yen` のない、前に作ったページは、いまの選べる金額のどれかであることを確かめる。本番の鍵（`sk_live_`・権限をしぼった `rk_live_`）のときはテストの知らせ（`livemode: false`）を、テストの鍵のときは本番の知らせを信じない。同じ決済の知らせは 1 回だけ数える（`payments`。決済の ID・金額・診断の ID だけを持ち、名前・メール・カードの情報は持たない。会計のため、診断を消しても残す）
  - 署名が正しく、払われていて（`payment_status: paid`）、`metadata.survey_id` がある知らせは、金額や通貨が合わなくても `payments` に残す（お金の記録をなくさないため）。そのときは特典を開かず、決済の ID だけを記録（`console.error`）に出す。運営者が確かめて返金する（返金の知らせで `refunded_at` が付き、数から外れる）
  - 返金・取り消しの済んだ支払い（同じ決済の ID か、同じ `payment_intent` の `payments` に `refunded_at` がある）の知らせが送り直されても、特典を開き直さない
- 全額の返金（`charge.refunded` で `refunded` が true）と、カード会社による支払いの取り消し（`charge.dispute.created`）の知らせを受けたら、その支払い（`payments.payment_intent` で結びつける）に `refunded_at` を付け、ほかに有効な支払いがなければ特典を閉じる（`premium_at`・`fortune_code` を消す）。一部だけの返金では閉じない。Stripe の Webhook の設定で、この 2 つの知らせも送るようにする
  - カード会社による取り消しの審査で、たこ診の側が認められた（`charge.dispute.closed` で `status: won`）ときも、特典は自動では開き直さない（閉じたままにする）。開き直すかどうかは、運営者が確かめて決める（知らせだけで開き直すと、取り消しと開き直しが行き来して分かりにくくなるため。控えめな側に倒す）
- くわしい分析：タイプごとの読み物と、その人の結果から組み立てた読み解き、問いごとのデータ。はじめの説明で、どこがタイプ共通の読み物で、どこが友達の答えから作った部分かを書く。「学び方・仕事の進め方」の章の終わりに「分野や仕事の例は遊びのヒント」、「疲れやすいところ」の章の終わりに相談をすすめる一文を置く。「セルフ・モニタリング」「社会的な自己」の説明には、見方のちがいやたまたまのこともあると添える
  - 読み物（`src/data/deepTypes.ts`）：よくある性格タイプの解説ページを参考にした章立て（概要・強み 5 つ・気をつけたいところ 4 つ・恋愛とパートナー・友人関係・学び方と仕事の進め方・学校やバイトや職場での姿・疲れやすいところと立て直し方・伸びしろ・まとめ）で、1 タイプおよそ 5,000 字。結果の画面で無料で見られる文（`types.json`）の言い換えにしない。ほかのサイトの文や呼び名はまねしない。性別を決めつけない
  - 心理学の要素：「疲れやすいところ」と「伸びしろ」に、定着した心理学の考え方を 1 つずつ、名前と平易な説明つきで入れる（研究者名・年号・数値・「証明された」は書かない）。性格タイプそのものに科学的な裏付けがあるとは書かない
  - その人の結果から（`src/lib/deepAnalysis.ts`）：4 つの軸それぞれの出方（しっかり・やや・ほぼ半々の 3 段階の文。`src/data/deepAxes.ts`）。§7.3 の散らばりで文を変える：寄った軸は、そろっていれば「どの相手にも同じように伝わっている」、分かれていれば「反対の面を知っている人もいる」、真ん中寄りなら「さりげなく出している面」の文を足す。ほぼ半々の軸は、分かれていれば「相手によって切りかえる」、真ん中寄りなら「どちらにも偏らない」の文に置きかえる。分かれた軸は、自己回答があれば自分ではどちらだと思っているかを添える。2 つ以上の軸で分かれたとき・3 つ以上の軸でそろったときは、まとめの一文を足す（分かれたときは、「社会的な自己」の考え方で説明。研究者名は書かない）。人数は書かず、「〜ようです」「〜かもしれません」と控えめに書く、友達の答えがいちばんそろった問いと、はっきり分かれた問い（そろった問いよりばらつきが 0.5 以上大きいときだけ。「セルフ・モニタリング」の考え方で説明）、自己回答があればジョハリの窓（開放の窓：自分も周りも 5 以上／盲点の窓：周りの平均 5 以上で自分は 4 以下、差 1.5 以上／秘密の窓：自分 5 以上で周りの平均 3.5 以下、差 1.5 以上。2 つずつまで）
  - 友達 1 人ずつの見え方（`src/components/DotPlot.tsx`）：答えた人が 10 人以上のときだけ、「4 つの軸の出方」の下に出す。軸ごとに横 1 本の線を引き、友達 1 人の軸の点（§6.2）を 1 つの点として、9 段階（左右で同じ幅に丸める。`dotBin`）の位置に積み上げる。線の左はしほど左の極、右はしほど右の極。結果で選ばれた側に寄った人の点は塗り、反対の側とちょうど 0 点の人は白抜き（真ん中の段階の点も、少しでも寄った側で分ける。`mid`）。線の下に、▲みんなの平均（結果の割合と同じ位置）と、◆中央値（順に並べて真ん中の人。偶数なら真ん中の 2 人の間。匿名性のため点と同じ 9 段階に丸める）。線の下に §7.3 の言葉を添える
    - 匿名性：点 1 つが 1 人なので、少ない人数では出さない（10 人未満では作らず、サーバーから送らない）。位置は 9 段階に丸め、軸どうしで同じ人の点をつながない（4 つの軸の組み合わせで、だれの点かしぼり込めないように）。関係ごとの色分けはしない
  - 目次つきで、最後に「答えのくわしいデータ」（開くと見える）として、問いごとの答えの分かれ方（そう思う・どちらとも・ちがうの人数）、意見がそろった問い・分かれた問い（3 つずつ）、自己回答と周りの平均の差が大きい問い（3 つまで）。§8.5 の決まりは特典でも同じで、1〜7 で答えた人が 3 人以上いる問いだけを出し、関係ごとの内訳とは掛け合わせない。人数をふやして出し直したときは、前に結果を出したときとくらべて、答えた人の数が変わらないか 3 人以上増えた問いだけを出す（`surveys.shown_counts` に、結果を出したときの回答の数を覚える）。平均とばらつきは、組み合わせると 1 人ずつの答えが割り出せるので、サーバーの中だけで使い（向き・分かれた問い・ジョハリの窓をサーバーで選ぶ）、送らない。なお、§8.4 のとおりホストが友達のふりをして答えると、ほかの人の答えをしぼり込めてしまう点は、特典でも防げない
  - 版 1（24 問）で出た結果は、保存した回答が版 1 の問の番号で並んでいるので、版 1 の要約と軸（A1→A4 のくり返し）で数える。極を持っていないので、図と §7.3 の散らばりは出さない
- スペシャルなシェア画像：金の枠・きらめき・「SPECIAL」の札（タコ占いへの案内は入れない）。「応援する」を押した診断と、特典を開いた診断だけ作れる。見せる場所は応援した人の欄だけにし、ふつうのシェアの欄（保存のボタンの下など）には置かない：「応援する」を押しただけなら応援のお願いの 2 段目に、支払いが済んだら（応援のお願いは出なくなるので）「スペシャルなシェア画像」の欄に、縦と横の見本と保存のボタンを出す
- タコ占い（`/uranai`）：シェア画像は 1 枚の絵で裏面を持てないので、合言葉で開くページを「裏」とする。支払いが済んだ診断に合言葉（`TAKO-XXXX-XXXX`。読みまちがえやすい I・L・O・U を除いた 32 文字 × 8 ＝ 40 ビットの乱数。`surveys.fortune_code`）を 1 つ作り、その診断の結果の画面にだけ出す。見られるのは応援した本人だけとし、「人に教えないでね」と書く。合言葉のまちがいが同じ回線から 10 回続いたら 1 時間止める（止めている間は確かめもしない）
  - 中身（`src/data/fortunes.ts`）：タイプに刺さる一言（タイプごとに 8 つ）・あるある（20）・アドバイス（20）から、人＝診断ごとに 1 つずつ選ぶ（タイプごとに 8 × 20 × 20 ＝ 3200 通り）。今日の運勢（総合・恋愛・友情・勉強や仕事を 5 段階）・今日のひとこと（232）・ラッキードリンク（40）・ラッキーカラー（30）は、人と日本時間の日ごとに決まる。占いの文は、一言・あるある・アドバイス（16 タイプで 768）と今日のひとこと（232）を合わせて 1000。同じ人が同じ日に見れば同じ結果になる
  - 合言葉で見せるのはタイプと占いだけで、呼び名は出さない。娯楽の占いで根拠はないと書く
  - 応援のお願いの 2 段目では、「1 枚目：表（スペシャルなシェア画像）」と「2 枚目：裏（あなたのタコ占い）」を横に並べ（指で送れる）、2 枚目にぼかしとモザイクをかけて「応援で続きが見られます」と案内する（金額は金額を選ぶところにだけ出し、同じ言葉を何度も出さない）。2 段目の文は短くし、特典の説明は 1 行ずつにする。支払いの前は本当の占いの文を送らず（ぼかしは外せるため）、形だけ同じ仮の文をぼかしの下に置く
- 特典は、その診断の保存期限（結果が出てから 180 日）まで見られる。特典を開いた診断は、結果が出たあとは人数をふやせない（§5.4。ふやすと結果と保存期限が消え、利用規約 第4条の2 や `/legal` の「結果が出てから 180 日見られる」に反するため）
- 応援のお願いの集計（/admin）：診断ごとに 1 行（`support_records`）で、応援のお願いを見た日（日本時間）と、「応援する」・「今回は閉じる」・支払いのページを開いた・支払った、の日時を持つ。行の ID は診断の ID とは別の乱数で、診断（`surveys.support_record_id`）からだけたどれる。診断を消すと、どの診断の記録かは分からなくなり、件数としてだけ残る。400 日で消す
  - 見たことは、応援のお願いが画面に出たときに記録する（`POST /api/host/support`、`seen`。「今回は閉じる」は `closed`）。「応援する」は贈り物、支払いのページは `/api/host/premium`、支払いは Stripe の知らせで記録する
  - /admin では、最近 7 日・30 日・すべてで、「応援するを押した／押していない」×「支払った／支払っていない」の 4 通りの件数と、見た診断に対する割合を出す。押していない・支払っていないのうち「今回は閉じる」を押した件数と、支払いのページを開いたが支払っていない件数も出す
  - 支払いのボタンは「応援する」を押したあとにだけ出るので、「押していない・支払った」はふつう 0 件

### 4.12 シェア

- 「画像で保存」：縦 1080×1920（ストーリー用）と横 1200×630 の 2 種
  - 画像のファイルを端末の共有の画面で渡せる端末（スマホの多く）では、ボタンを「縦を保存・共有」「横を保存・共有」とし、共有の画面で「画像を保存」を選ぶと写真に入ると添える。共有の画面を使わない「ダウンロード」も別に置く
  - 渡せない端末（パソコンの多く）では「縦をダウンロード」「横をダウンロード」とし、PNG をダウンロードする
  - 押したあとは、作成中・共有の画面を開いた・ダウンロードした・やめた（共有の画面を閉じた）・作れなかった、を分けて出す
- 文字の優先順位（初めて見た人にも、自分で答える診断とのちがいが伝わるように）：1. いちばん上に大きく「友達{N}人から見た／{呼び名}は、このタイプ」 2. タコ・タイプ名・4 文字 3. キャッチ 4. 4 軸の割合 5. 「たこ診｜友達が答える16タイプ診断」 6. サイトのアドレス。呼び名は 12 文字まで（日本語・英数字で確かめる）
- 画像に入れるのは：呼び名・4 文字・界隈・タイプ名・キャッチ・4 軸の % ・回答人数・アプリ名・サイトのアドレス（`NEXT_PUBLIC_SITE_URL` のホスト名。ストーリーなどリンクを付けられない場所で見た人がたどり着けるように。設定がなければ入れない）
- **自分で思うタイプ**（4 文字とタイプ名・小さなタコ）：自己回答があり、どの軸もど真ん中でないときだけ、画像に並べられる。周りとのずれは話題にしやすいので、チェックで外せる形で、はじめは入れる。サーバーも、この条件を満たすときだけ描く
- 画像に**入れない**もの：関係ごとの内訳、問いごとの答え（自己回答も友達の答えも）
- 結果の画面では、タイプのカードのすぐ下に「結果をシェアする」を置き、シェアの欄へ飛べるようにする。飛ぶのはボタンで、URL の # は書きかえない（§8.2）
- 「リンクで公開」：S7 用の URL を作る。ホストが押したときだけ作り、いつでも取り消せる
- S7 の下には「たこ診は、自分ではなく友達が答える 16 タイプ診断です」と「自分も友達に聞いてみる」（`/new?entry=public`）を置く
- 結果の画面のシェアの欄では、縦と横の画像の見本を並べて見せ、それぞれの下に保存のボタンを置く（見本は欄が画面に近づいてから作る）
- 「X に投稿」（黒地に白い文字）「LINE で送る」（LINE のアイコンと同じ緑 #06C755 の地に白い文字。白い文字との明るさの差は 2.3:1 で読みやすさの基準に届かないが、LINE の色をそろえることを優先する）

## 5. 状態と決まり

### 5.1 診断の状態

```
            作る
             │
             ▼
   ┌──── 受付中 ────┐
   │   (open)      │  N 人目が答える
   │               ├────────────→ 確定 (completed)
   │               │←────────────┤ 人数をふやす（§5.4）
   │ 期限が来る     │                  │
   ▼               │                  │ ホストが消す / 保存期限
 期限切れ (expired) │                  ▼
   │               │               削除 (データを物理削除)
   └── ホストが消す ─┴───────────────→
```

| 状態     | 回答の受付 | 結果の表示 | 自己回答 |
| -------- | ---------- | ---------- | -------- |
| 受付中   | する       | しない     | できる   |
| 確定     | しない     | する       | できない |
| 期限切れ | しない     | しない     | できない |

### 5.2 期限

- 受付中の期限：作ってから **30 日**。S5 から 1 回だけ **30 日延長**できる（合計 60 日まで）
- 確定した診断の保存期限：確定から **180 日**。過ぎたら全データを消す。S6 で残り日数を出す
- 期限切れの診断：期限切れから **30 日** で全データを消す
- 保存期限（`delete_at`）を過ぎた診断は、定時処理で消す前でも、ないものとして扱う（管理用リンク・公開リンクのどちらでも見えない）。古い版の問で作った受付中の診断も、定時処理で期限切れにする
- ホストはいつでも診断を消せる（確認ダイアログあり）。消したら元に戻せない
- 定時処理（1 日 1 回）は、片付けを 1 つずつ別に行い、どれかが失敗したら 500 を返す。`CRON_SECRET` がない・失敗したときは Workers Logs に記録し、Cron の実行結果も失敗にする（黙って止まると、保存期限を過ぎたデータが消えないことに気づけないため）

### 5.3 回答の受付の決まり

1. 受付中のときだけ受け付ける
2. 各軸で 3 問以上に 1〜7 の答えがあること。なければ受け付けない（画面でも先に止める）
3. **N 人目まで**しか受け付けない。同時に 2 人が最後の 1 枠に送ったときは、先にデータベースに入った 1 人だけを受け付け、もう 1 人には「ちょうど締め切られました。ありがとう！」と出す（§11.2 の方法で確実に守る）
4. 同じ端末からの 2 回目は受け付けない（§8.3）。ただし完全には防げない（§8.4）。回答者の乱数（cookie）は、招待のページを開いたとき（`/api/surveys/<ID>/public`）に先に渡す（送った返事が途中で切れて乱数を受け取れないと、送り直しが 2 人目として数えられてしまうため）
5. N 人目を受け付けたのと**同じ処理の中で**、結果を計算して保存し、状態を「確定」にする

### 5.4 人数をふやす

ホストは、トップの「つくった診断」、回答状況（S5）、結果（S6）から「人数をふやす」画面へ進み、人数をふやせる。ふやすときは、ホストが見ていた状態（受付中・確定）も送り、いまの状態とちがえば断る（受付中のつもりでふやす間に結果が出ていたら、見ないまま結果を消してしまうため）。

- **同じ招待リンクのまま**受付を続ける。それまでの回答はそのまま使い、前に答えた人はもう一度は答えられない（§5.3 の 4）
- **受付中**：1 人以上ふやせる
- **確定**：**3 人以上**ふやす。受付中に戻し、新しい人数がそろったときに、全員の回答で結果を出し直す
  - 3 人以上にするのは、1〜2 人だけふやすと、前の結果と新しい結果の差から、あとから答えた人の答えの傾向が分かってしまうため（§8.5）
  - 全体で 3 人以上ふやしても、深掘りの問や「わからない」のため、問ごと・関係ごとには 1〜2 人しか増えないことがある。そこで、問ごとの文（§7.5 の D5〜D7）・関係ごとの見え方（§7.7）・くわしい分析の問ごとの集計（§4.11）は、前に結果を出したときの数とくらべて、変わらないか 3 人以上増えたものだけを出す
  - それまでの結果・公開リンク（S7）は消す。公開していた場合は、新しい結果が出てから作り直す
  - 受付の期限は、ふやした日から 30 日にし、延長（§5.2）をもう一度使えるようにする
- 上限は 30 人。期限切れの診断と、古い版の問（§6.8）で作った診断はふやせない
- 特典つきの応援で特典を開いた（`premium_at` がある）診断は、結果が出たあとはふやせない。結果と特典を、結果が出てから 180 日見られる約束（利用規約 第4条の2・`/legal`・Stripe の支払いのページ）を守るため。`raiseMin` を null にし、サーバーも断る（`premium`）。「人数をふやす」画面では「特典を開いた診断は、結果と特典を 180 日のこすため、人数をふやせません」と出す
- 結果が出た診断をふやすとき、特典の支払いのページ（`checkout_session_id`）を開いていたら、先に閉じる（受付中に戻ったあとで払われないように）。もう払われていたか、確かめられないときはふやさない（`paying`。「特典つきの応援の支払いを確かめています。少し待ってから、もう一度試してください」）
- 人数はへらせない
- 行の鍵をかけた 1 つの処理の中で確かめて書きかえる（N 人目の回答と同時に来ても、どちらか一方の順になる）
- ふやしたあとは、招待リンクの共有画面（S4）へ進む

## 6. 判定の計算

計算はすべてサーバーで、**整数だけ**を使って行う（小数の誤差で「ちょうど半々」の判定がずれないように）。

### 6.1 1 問の点

回答 `a`（1〜7）から `v = a − 4`（−3〜+3）を作る。
その問が**左の極向き**（E・S・T・J）なら `s = v`、**右の極向き**（I・N・F・P）なら `s = −v`。
つまり `s` が正なら左の極、負なら右の極に寄っている。「わからない」は計算に入れない。

### 6.2 1 人の軸の点

回答者 `r` の軸 `k` の点：

```
x(r,k) = (その軸で答えた問の s の合計) × 840 ÷ (その軸で答えた問の数)
```

答えた問の数は 3〜8（深掘りした軸は最大 8 問）で、840 は 1〜8 のどれでも割り切れるので、`x` は必ず整数になる（−2520〜+2520）。
840 を掛けて問の数で割るのは、答えた問の数がちがう人どうし（深掘りした人・しない人、「わからない」が多い人）を同じ重みで比べるため（1 人 1 票）。
「わからない」と、出していない問は計算に入れない。

### 6.3 全員の軸の点

```
X(k) = Σ_r x(r,k)          （N 人分の合計、整数）
平均 = X(k) ÷ N            （−2520〜+2520）
左の極の割合(%) = 50 + 平均 ÷ 2520 × 50   →  四捨五入で整数に（0〜100）
```

- `X(k) > 0` → 左の極（E・S・T・J）
- `X(k) < 0` → 右の極（I・N・F・P）
- `X(k) = 0` → §6.4

画面には**選ばれた極の割合**を出す（例：右の極なら `100 − 左の割合`）。四捨五入の結果がちょうど 50% でも、`X(k)` の符号で決めた極を出す。

### 6.4 ちょうど半々のとき（`X(k) = 0`）

次の順に決める。前の手順で決まれば、そこで止める。

1. `x(r,k) > 0` の人数と `x(r,k) < 0` の人数を比べ、多いほう
2. 自己回答があれば、その軸の自己の点の符号
3. 「強くそう思う」寄りの答え（`|s| = 3`）だけを足した合計の符号
4. それでも決まらなければ、右の極（I・N・F・P）にする（決まりを固定しておくため。理由は特にない）

いずれの場合も、その軸に「**ど真ん中**」の印を付け、分析文で必ず触れる（§7.5）。

### 6.5 一致の度合い

軸ごとに、点がちょうど 0 でない人（`x(r,k) ≠ 0`。「どちらとも言えない」の人は、同じ向きにも反対の向きにも数えない）のうち、
選ばれた極と同じ向きの人の割合 `c` を出す。

| 条件                                  | 表示         |
| ------------------------------------- | ------------ |
| N 人全員が同じ向き（0 の人もいない）  | 満場一致     |
| `c ≥ 75%`                             | ほぼ一致     |
| `50% < c < 75%`                       | 多数派       |
| `c ≤ 50%`（0 でない人がいないときも） | 意見が割れた |

（`c ≤ 50%` でも、極は `X(k)` の合計で決まる。少数の人が強く答えた場合に起こる。分析文で触れる。）

0 の人を分母に入れると、「強く外向 1 人＋どちらとも 2 人」で反対が 0 人なのに「意見が割れた」になり、D4 の文（§7.5）が
「見せている顔が相手によってちがう」と事実と合わないことを書いてしまうため、分母から外す（版 1.38 で直した。確定済みの結果は変えない）。

### 6.6 寄り具合の言葉

選ばれた極の割合 `p` から：

| `p`     | 言葉     |
| ------- | -------- |
| 50〜54  | ほぼ半々 |
| 55〜64  | やや     |
| 65〜79  | しっかり |
| 80〜100 | 振り切れ |

### 6.7 自己回答の点

自己回答も §6.1〜6.2 と同じ式で `x(self,k)` を出し、割合 `p_self` に直す。
自己回答は**全員の点 `X(k)` に入れない**（あくまで「周りから見た」結果にするため。ただし §6.4 の 2 で半々のときだけ使う）。

### 6.8 計算の版

計算の決まりを将来変えても、確定済みの結果は変えない。結果に `algorithmVersion` を保存する。

- 版 1：24 問・全員が全問に答える・目盛り 60
- 版 2（いま）：32 問から 16〜32 問を出す（§3.5）・目盛り 840。版 1 で確定した結果の分析の文（D5〜D7）は、版 1 の問の要約で出す
- 診断にも作ったときの問の版（`question_version`）を保存する。今の版でない問で作った受付中の診断は、答えを混ぜられないので期限切れとして扱う

### 6.9 計算例（テストにも使う）

N = 3、軸 A1 だけを例にとる（基本 Q1〜Q4・深掘り Q5〜Q8）。

| 回答者 | Q1(E) | Q2(I) | Q3(E)      | Q4(I) | Q5(E) | Q6(I) | Q7(E) | Q8(I) |
| ------ | ----- | ----- | ---------- | ----- | ----- | ----- | ----- | ----- |
| r1     | 7     | 2     | 6          | 3     | —     | —     | —     | —     |
| r2     | 5     | 4     | わからない | 3     | 5     | 3     | 4     | 5     |
| r3     | 3     | 5     | 4          | 6     | —     | —     | —     | —     |

（— は出していない問）

- r1：基本 s = (+3, +2, +2, +1) → 合計 8、4 問。|8| ≥ 4 なので深掘りしない → x = 8×840÷4 = **1680**
- r2：基本 s = (+1, 0, —, +1) → 合計 2、3 問。|2| < 3 なので深掘りする。深掘り s = (+1, +1, 0, −1) → 全部で合計 3、7 問 → x = 3×840÷7 = **360**
- r3：基本 s = (−1, −1, 0, −2) → 合計 −4、4 問。|−4| ≥ 4 なので深掘りしない → x = −4×840÷4 = **−840**
- X = 1680 + 360 − 840 = **1200** > 0 → **E**
- 平均 = 1200 ÷ 3 = 400 → E の割合 = 50 + 400÷2520×50 ≈ 57.94 → **58%**（やや外向）
- 一致：E 向きは r1・r2 の 2 人 → c = 67% → **多数派**

## 7. 分析文

### 7.1 方針

- 「正しい」：数字に裏付けのない言い切りをしない。データから言えることは数字を添えて言い、タイプの一般的な傾向は「〜と見られがち」「〜タイプ」と書く
- 「詳しい」：タイプの文（全員共通）に、その人の回答から作る文（その人だけ）を重ねる
- 「面白い」：友達あるある・具体的な場面・軽いツッコミで書く。ただし相手を傷つける言い方、外見・能力・性別・恋愛の決めつけはしない
- 長さの目安：全部開いて 1,500〜2,500 字

### 7.2 タイプのカード

§2.3 の、4 文字・界隈・タイプ名・キャッチ・タグを出す。
4 文字はタイプ名のすぐ上に、タイプ名と同じくらいの大きさで出す（いちばん目に入り、ほかの診断と見比べやすいように）。
4 つの軸のうち「ど真ん中」があれば、カードの 4 文字のその文字を半分ずつの色にし、小さく「どっちも」と添える。

**入れ替わりやすい軸**：ど真ん中でない軸のうち `p` が 55 未満（ほぼ半々。§6.6）の文字には、点線の下線を引き、「点線の文字はほぼ半々。別の友達に聞くと入れかわるかも」と添える（読み上げでは「ほぼ半々」と読む）。4 文字型は真ん中近くの人ほど少しの差で文字が変わり、そのほとんどは 1 つの軸だけが半々に近いことで起きる。全体の「ゆるめの判定」だけでは、これを伝えられないため。文字を薄くすると地の色との明るさの差が足りなくなるので、白いまま点線で示す。点線は文字の下線（text-decoration）ではなく、文字ごとに少し下へ離して描き、となりの文字の点線とつながらないようにする（文字に重なって見づらくならないように）。公開リンクの結果カード（S7）も同じ。

**ゆるめの判定**：4 軸すべての `p` が 65 未満（どの軸も「しっかり」に届かない。§6.6）なら、キャッチの下に「**ゆるめの判定**：どの軸も強くは出ていないので、ほかのタイプにも少しずつ当てはまります」と添える。4 文字は出るが、言い切れるほどではないことを正直に伝えるため（ゆるめも個性として前向きに書く）。公開リンクの結果カード（S7）も同じ。

### 7.3 4 軸メーター

軸ごとに 1 本の横長の帯。左右に極の名前、選ばれた側に割合。「寄り具合の言葉」「一致の度合い」は分かりにくいため出さない。帯の下に「％は人数の割合ではなく、友達の答えの寄り具合です（50% がちょうど半々、全員が最も強く答えると 100%）」と書く（人数の割合とまちがえやすいため）。

帯の下には、友達の見え方の散らばりを 1 つの言葉で添える（`axisSpreads`。割合が同じでも、全員が少しずつ寄ったのか、両側にはっきり分かれたのかは意味がちがうため）。1 人ずつの軸の点（§6.2）で、1 問あたり平均 ±1 以上（§3.5 の深掘りの境目と同じ）を「はっきり寄った」とみなす。

| 言葉                       | 決まり                                                                                                                     |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| 友達の見え方がそろっている | 一致の度合いが「満場一致」か「ほぼ一致」で、反対側にはっきり寄った人がいなく、半分以上の人が選ばれた側にはっきり寄っている |
| 人によって見え方がちがう   | 両側に、それぞれ 4 分の 1 以上の人がはっきり寄っていて、一致の度合いが「多数派」か「意見が割れた」                         |
| 多くの友達が真ん中寄り     | 反対側にはっきり寄った人がいなく、半分より多くの人がどちらにもはっきりとは寄っていない                                     |

- どれにも当たらない軸には、何も添えない（言い切れないときは言わない）
- 人数は出さない（§8.5）
- 保存した回答から、結果を見るときに計算する。散らばりを足す前に出た結果にも出る
- 見本（シミュレーション。友達 3 人）：そろっている 36〜43%・ちがう 7〜24%（見る人ごとのずれが大きいほど多い）・真ん中寄り 28〜41%・言葉なし 9〜13%

```
外向 ━━━━━━━●━━━━ 61% 内向
```

自己回答があるときは、4 軸メーターを出さず、§7.6 の「周りと自分の比較」に置きかえる（同じ帯を 2 回見せない）。

### 7.5 データでわかるあなた（回答から自動で作る文）

次の規則で、条件を満たすものを**上から最大 6 つ**まで出す。数字はすべて実際の回答から入れる。

| 規則                    | 条件                                                                                                                                                                              | 文の型（例）                                                                                            |
| ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| D1 いちばん強い軸       | 寄り具合 `p` が最も大きい軸（同じなら A1→A4 の順で先）。その軸もど真ん中なら出さない                                                                                              | 「いちばんハッキリ出たのは **{極名}**（{p}%）。{N} 人から見て、ここはあなたの「看板」です」             |
| D2 満場一致             | 一致が「満場一致」の軸（複数あれば 1 つの文にまとめる）                                                                                                                           | 「**{極名}・{極名}** は {N} 人全員の意見が一致。だれの目にもそう映っています」                          |
| D3 ど真ん中             | §6.4 の印がある軸（複数あれば 1 つの文にまとめる）                                                                                                                                | 「**{左極名}** と **{右極名}** はちょうど半々。場面や相手によって使い分けているようです」               |
| D4 意見が割れた         | 一致が「意見が割れた」の軸のうち、ど真ん中でなく、D8 にも当たらないもの（複数あれば 1 つの文にまとめる）                                                                          | 「**{軸名}** は意見が割れました。見せている顔が、相手によってちがうのかも」                             |
| D5 みんなが認めた行動   | 1〜7 で答えた人のうち 5 以上を選んだ割合が最も高い問（3 分の 2 以上のときだけ。同じなら番号の若い問）                                                                             | 「{答えた人数} 人中 {人数} 人が『{質問の要約}』に「そう思う」。友達の目にもはっきり映っている行動です」 |
| D6 みんなが否定した行動 | 3 以下を選んだ割合が最も高い問（3 分の 2 以上のときだけ）                                                                                                                         | 「『{質問の要約}』は {人数} 人が「ちがう」。友達から見ると、あまりしない行動のようです」                |
| D7 謎の行動             | 「わからない」を選んだ人が最も多い問（半数以上のときだけ）                                                                                                                        | 「『{質問の要約}』は {人数} 人が「わからない」。ここはまだ友達に見せていない一面かも」                  |
| D8 少数の強い声         | 一致が「意見が割れた」で、ど真ん中でなく、選ばれた極の向きの人数が反対の向きの人数以下の軸（＝人数では勝っていないのに、強い答えの合計で決まった。複数あれば 1 つの文にまとめる） | 「人数では割れたけど、強く感じている人の声で決まりました：**{軸名}** は **{極名}**」                    |

- 同じ規則に当たる軸が複数あっても 1 つの文にまとめる。同じ言い回しの文が続いて 6 つの枠を埋め、D5〜D8 のような回答ならではの文が押し出されるのを防ぐため
- ど真ん中の軸は D3 で触れるので、D4 には入れない（全員がちょうど 0 の軸は一致の度合いが「意見が割れた」になるが、実際には割れていないため）。一致の度合いは 0 の人を分母に入れないので（§6.5）、D4 が出るのは反対の向きの人が 1 人以上いるときだけ
- 「質問の要約」は、質問ごとに用意した短い言い方を使う（例：Q1 →「初対面でも自分から話しかける」）。§11.4 `src/data/questions.ts` の `summary`
- 人数は「{答えた人数} 人中」と書き、「わからない」の人を分母に入れない
- D5〜D7 は、その問を出した人だけで数える。深掘りの問は一部の人にしか出ないので、D5・D6 は**1〜7 で答えた人が 3 人以上**、D7 は**その問を出した人が 3 人以上**の問だけを使う（少ない人数だと、だれの答えか分かってしまうため。「わからない」が 2 人いて 1 人だけ答えた問で「1 人中 1 人」と出さない）。人数をふやして出し直したときは §5.4 の差の決まりも守る
- 割合の表し方：全員のときは「全員」と添える。それ以外は人数だけで書く
- D1 で「看板」と言い切るのは `p` が 65 以上（しっかり）のときだけ。65 未満なら「いちばん出たのは **{極名}**（{p}%）。ただ、どの軸も強くは出ておらず、ほかのタイプの顔も少しずつ持っています」（D1 は最も強い軸なので、このときはゆるめの判定（§7.2）と同じ状態）
- D5・D6 の行動が、その問の軸の判定と逆向きに見えるとき（判定は内向なのに、外向の問に「そう思う」が多い。または判定と同じ極の問に「ちがう」が多い）は、ずれをはっきり書く。そのまま書くと「全員が話しかけると言っているのに内向？」と矛盾して見えるため
  - D5：「{答えた人数} 人中 {人数} 人が『{質問の要約}』に「そう思う」。判定は{わずかに} **{判定の極}**（{p}%）でも、この場面では **{問の極}** の顔がみんなに見えています」
  - D6：「『{質問の要約}』は {答えた人数} 人中 {人数} 人が「ちがう」。判定は{わずかに} **{判定の極}**（{p}%）でも、この行動はあまり見られていないようです」
  - 「わずかに」は `p` が 55 未満（ほぼ半々）のときだけ付ける。ど真ん中の軸は両方の顔があるので、ずれとは言わない。1 版（24 問）の結果は問の番号がちがうので、これまでの文のまま

### 7.6 周りと自分の比較（自己回答があるときだけ）

結果の画面では、4 軸メーターの場所（パソコンでは左の列）に置く。軸ごとに、周り（上）と自己（下）の割合を並べた図（2 本の帯）を出し、下に 1 つだけ「周りから見たあなた／自分で思うあなた」の見分け方を添える。そのあとに次の文を付ける。自分で思うタイプ（タイプ名と 4 文字）は、ど真ん中の軸がないときだけ出す。

| 条件                                          | 文の型                                                                                                                                                        |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 極がちがう                                    | 「自分では **{自己の極}** だと思っているけど、周りからは **{周りの極}** に見えています。意外な一面が外に出ているのかも」                                      |
| 極は同じで、差が 20 ポイント以上              | 「どちらも **{極}** だけど、周りのほうが {多い/少ない}。自分が思うより{強く/控えめに}出ています」                                                             |
| 自分の点がちょうど 0 で、周りはど真ん中でない | 「自分では **どちらとも言えない** と思っているけど、周りからは **{周りの極}** 寄り（{p}%）に見えています」（70% 以上なら「ハッキリ **{周りの極}**（{p}%）」） |
| 自分も周りもど真ん中                          | 「自分でも周りから見ても **どちらとも言えない**（50%）。場面によって両方の顔が出ているようです」                                                              |
| 差が 20 ポイント未満                          | 「自分の見方と周りの見方がほぼ一致。自分をよく分かっています」                                                                                                |

自分の点がちょうど 0 の軸は、§6.4 の手順 4 に合わせて右の極として扱う（自分で思うタイプの 4 文字に使う）が、「極がちがう」とは言わない（どちらとも答えていない人に「〜だと思っている」とは言えないため）。
4 軸すべてが「ほぼ一致」で、自分がど真ん中の軸がないときだけ、まとめに「自己理解の達人」と出す（どちらとも答えていない軸は、見方が一致したとは言えないため。以前の決まりで保存した結果も、表示のときに同じ決まりで出す）。自分がど真ん中の軸の帯は、どちらの側にも色を付けず、読み上げも「どちらとも言えない（50%）」とする。2 軸以上で極がちがえば「ギャップ萌えタイプ」と出す。
自分で思うタイプは、ど真ん中の軸がないときだけ「自分で思うタイプ：{タイプ名}（{4 文字}）」と出す（ど真ん中の軸があると 4 文字が決まりきらないため）。

### 7.7 関係ごとの見え方

X1 で同じ関係を選んだ人が **3 人以上いる関係が 2 つ以上**あるときだけ出す（少ない人数で出すと、だれが答えたか分かってしまうため）。
その関係の人だけで §6 と同じ計算をして、関係ごとのタイプ名を並べる。

> 例：「同じ学校の友達から見ると **お祭り番長**、職場・バイトの人から見ると **現場監督**。場所によってキャラを使い分けています」

### 7.8 相性のいいタイプ（遊び）

タイプごとに 2 つ決めておく（§12）。「一緒にいるとラク」「刺激をくれる」の 2 種類。
科学的な根拠はないので、見出しに「おまけ」と書き、「相性に正解はありません」と添える。

### 7.9 文の言い方の決まり

- 呼びかけは「あなた」。ホストの呼び名は質問文だけで使う
- 「〜です／〜ます」の丁寧な話し言葉を基本にし、尊敬語・謙譲語は使わない。「あるある」などのひとこと部分だけはくだけてよい
- 絵文字は使わない（環境で見た目が変わるため。代わりに自前の小さな絵を使う）
- 「〜すべき」「〜しなさい」は使わない

## 8. 匿名性・安全

### 8.1 集める情報

| 情報                                   | 集める                                     | 理由                                                                                                                                                                             |
| -------------------------------------- | ------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ホストの呼び名                         | する                                       | 質問文に入れるため。本名でなくてよいと画面に書く                                                                                                                                 |
| 回答（16〜32 問・関係）                | する                                       | 判定のため                                                                                                                                                                       |
| メールアドレス・電話番号・アカウント   | **しない**                                 | 不要。登録なしで使える方が気軽                                                                                                                                                   |
| 通知の送り先（ブラウザの購読）         | ホストが「通知を受け取る」を押したときだけ | 「全員そろった」を 1 回知らせるため。送ったら消す（§11.10）。送り先は端末ごとに 1 つなので、同じ端末の複数の診断は受付中のあいだ結びつく（使わない。プライバシーポリシーに書く） |
| IP アドレス                            | 保存しない                                 | 連続投稿の制限に一時的に使うだけ（§8.4）                                                                                                                                         |
| 端末の識別子                           | 診断ごとの乱数だけ                         | 二重回答の防止。端末をまたいだ追跡はしない                                                                                                                                       |
| リンクが開かれた回数                   | 日・ページ・送り方ごとの件数だけ           | どの送り方で使われているかを運営者が知るため（下記）。だれが・どの診断かは残さない                                                                                               |
| 利用の流れの件数・診断ごとの利用の記録 | 決まった値と日時だけ（§11.11）             | 人が来ない・回答が集まらない・結果から広がらない、を見分けるため。呼び名・回答・管理用の鍵は入れない                                                                             |

**リンクが開かれた回数**：招待リンク（`/a/`）・公開リンク（`/r/`）・結果をシェアしたときのトップに、送り方の目印 `?from=` を付ける
（`line`・`x`・`qr`・`copy`・`share`。招待リンクの画面の「その他」は `share`）。ページを開いたブラウザが `/api/visit` にページの種類と目印だけを送り、
サーバーは日本時間の日・ページ・送り方ごとの件数（`visit_counts`）に 1 を足す。目印のない招待リンク・公開リンクは「目印なし」として数え、トップは目印があるときだけ数える。

- 数えたあと、アドレスから `?from=` を外す（そのアドレスを送り直したときに、元の送り方として数えないように）
- ページのスクリプトを動かさない機械（LINE や X がリンクの見出しを作るための読み込み）は数えない。名乗りが機械のものも数えない
- 同じ回線から同じページの種類は 1 時間に 10 件まで（§8.4 と同じ仕組み）
- 件数は 400 日で消す。運営者は `/admin` で最近 7 日・30 日の件数を見る
- ほかの事業者のアクセス解析（Cloudflare Web Analytics など）は使わない。URL のパスに招待リンクの ID が入るため（§8.2）

### 8.2 鍵の作り方

- `surveyId`（招待リンク）・`hostKey`（管理リンク）・`shareId`（公開リンク）は、それぞれ別に作った暗号的に安全な乱数（128 ビット以上、URL に使える文字で 22 文字程度）
- データベースには `hostKey` そのものではなく、その**ハッシュ値（SHA-256）**を保存する。データベースが漏れても管理画面に入れないようにするため
- 招待リンクから管理リンクを知る方法はない
- 管理用のリンクは `/h#{hostKey}` の形にし、API には `X-Host-Key` という見出し（ヘッダー）で渡す。URL のパスに入れないので、アクセスしたアドレスの記録には残らない
- Cloudflare の Workers Logs の通信ごとの記録（invocation logs）は、見出しを丸ごと残す（`x-host-key`・cookie・`cf-connecting-ip` を含むことを、2026-10-29 に管理画面で確かめた）。そのため `wrangler.jsonc` で `observability.logs.invocation_logs: false` にして止める。`console.log`・`console.error` で書いた記録（定時処理の結果など）は残る
- すべてのページで `Referrer-Policy: no-referrer` を返す
- 管理用のページでは、ページの中の見出しへ移るのに `<a href="#…">` を使わない（# の後ろの鍵が書きかわり、再読み込みや新しいタブで「診断が見つかりません」になるため）。ボタンで見出しまでスクロールする
- 画面の中の移動のあと、新しい画面を描いた時点では URL がまだ前のままのことがある。鍵がないと決めるのは描き終えたあとにし、「診断が見つかりません」を一瞬でも描かない（画面の切りかえの読み上げに残るため）

### 8.3 端末に保存するもの

| 保存先                                                     | 中身                                                 | 用途                                            |
| ---------------------------------------------------------- | ---------------------------------------------------- | ----------------------------------------------- |
| ホストの端末（ブラウザの保存領域）                         | 作った診断の `hostKey` の一覧                        | S1 の「つくった診断」・ホスト自身の回答を止める |
| ホストの端末（ブラウザの保存領域）                         | 通知を受け取る設定にした送り先のアドレス（診断ごと） | S5 で「通知をやめる」を出す（§11.10）           |
| 回答者の端末                                               | 答えかけの回答                                       | 途中から続ける                                  |
| 回答者の端末＋サーバーが読む小さな記録（cookie、httpOnly） | 診断ごとの回答者の乱数                               | 同じ端末の二重回答を止める                      |

- 診断ごとの cookie（回答者の乱数 `tkr_<ID>`・ホストの印 `tkh_<ID>`）は、その診断の API（`/api/surveys/<ID>`）にだけ送られるように付ける。どのページにも送ると、その端末が作った診断・答えた診断の一覧が毎回送られ、運営側で結びつけられるため。前に path=/ で付けた cookie は、招待のページを開いたときに付け直して消す
- 答えかけの回答は、送れたときのほか、締め切り・期限切れ・ホストの端末と分かったときにも消す（共有の端末で、ほかの人に読まれないように）
- シェア画像は端末にとっておかない（`no-store`）。画像のアドレスには鍵が入らないので、とっておくと、同じブラウザで開いた別の診断に前の診断の画像が出てしまうため

ブラウザの保存領域は、内緒モードなどで使えないことがある。そのときも画面が壊れないようにし、
ホストには「管理リンクを自分に送っておいて」と強めに案内する。

### 8.4 防げないこと（正直に書いておく）

- 別の端末や内緒モードを使えば、同じ人が何度も答えられる。またホストが友達のふりをして答えることもできる。登録なしで気軽に使える代わりの割り切りとする
  - ホストが友達のふりをして何人分も答えると、まとめた結果（とくにくわしい分析の問ごとの人数）から、残りの人の答えを推測できてしまう。そのため回答者の画面では「見えません」と約束せず「1 人ずつの答えは表示されません」と書き、プライバシーポリシーにこの限界を書き、利用規約で禁止する
- 被害を小さくするため、同じ IP アドレスからの同じ診断への回答は **1 時間に 20 件まで**（受け付けた回答だけ数え、重複・締め切り・形のまちがいは数えない。学校・会社・携帯電話の回線は多くの人で同じアドレスを使うため、ほかの操作の 10 件より多くする）。受け付けなかった送信は別に **1 時間に 60 件まで**（受け付けた分だけを数えると、拒否される送信を同じ診断に無限に投げて、その診断の行の鍵を取り合う処理を回され続けるため）
- API に送る本文は **16 KB まで**。超えていれば、回数を数える前に読まずに断る（巨大な JSON を読まされて CPU と記憶領域を使わされないため）。`Content-Length` は付けずに送ることもできるので、宣言だけに頼らず、読んだバイト数を数えて上限をこえたところで読むのをやめる（`readTextLimited`）。Stripe からの知らせ（`/api/stripe/webhook`）は 64 KB までとし、こえれば署名を確かめる前に 413 で断る
- 結果の画像（シェア画像 `/api/host/image`・公開リンクの見出し画像 `/api/og/<ID>`）は 1 枚ごとに描画するので、同じ IP アドレスから **1 時間に 120 枚まで**（見出し画像は公開リンクごとに数える）
- 回数はデータベースの `rate_limits` で数える（Cloudflare では処理を受け持つ isolate がいくつもあり、記憶の中で数えると台数の分だけゆるくなるため）。key は「IP アドレスと操作の種類」を、サーバーだけが知る鍵で HMAC-SHA256 にした値で、IP アドレスそのものは保存しない。鍵のないハッシュ値だと、IPv4 の約 43 億通りを試すだけで元のアドレスが分かり、「どの回線がどの診断に答えたか」を結びつけられてしまうため。鍵は `RATE_LIMIT_SECRET`、なければ `CRON_SECRET`、なければ `ADMIN_TOKEN` から作る（新しい設定はいらない。合言葉を替えると数え直しになるが、記録は 1 時間で切れるので困らない）。どれもないときは、手元とテストでは起動ごとの乱数、本番では決まった値にして記録に注意を残す。最初に数えた時から 1 時間で数え直し、1 時間を過ぎた記録はときどきと定時処理で消す。IPv6 は利用者ごとに /64 の範囲をもらうことが多く、その中でいくらでもアドレスを変えられるので、/64 でまとめて数える
- それでも、IP アドレスをいくつも使える相手は、他人の診断に偽の回答を流し込める（招待リンクは広く共有されるため）。防ぐには人の確認（Cloudflare Turnstile など）が要るが、外部の仕組みを読み込むことになるので、今回は入れない
- IP アドレスは、Cloudflare が付ける `CF-Connecting-IP` から読む。`X-Forwarded-For` の先頭は利用者が好きな値を送れる（Cloudflare は後ろに足すだけ）ので、制限をすり抜けられてしまうため
- 診断を作るのも、同じ IP アドレスから **1 時間に 10 件まで**（機械で大量に作られるのを防ぐ）
- 結果の注記で「回答は、答えた友達それぞれの見方です」と書く（本人の自己申告ではないため）

### 8.5 匿名性の決まり

- ホストには、だれが何と答えたかを**どの画面でも出さない**
- 1 人分の回答を推測できる表示をしない：人数の下限 3 人（§4.3）、関係ごとの表示は 3 人以上（§7.7）、結果が出たあとに人数をふやすときは 3 人以上（§5.4）、深掘りの問を使う分析の文は 3 人以上に出した問だけ（§7.5）。回答者が自由に文を書く欄は設けない（書きぶりで人が分かり、悪口の場にもなりうるため）
- 1 人分の点の計算に使える細かい値を送らない：軸の合計点（`sum`）は結果に入れず、前に保存した結果からも外して返す。くわしい分析の平均・ばらつきも送らない（§4.11）
- 関係ごとの見え方の並びは、関係の名前の順にする（届いた順にすると、最初に答えた人の関係が分かるため）
- 回答の時刻を画面に出さない（「さっき答えた人がこう答えた」と分かるため）。S5 の丸は、答えた数だけ色が付くことしか示さない

### 8.6 そのほかの安全

- 呼び名は表示のとき必ず文字として扱い、HTML として解釈しない（スクリプトの埋め込みを防ぐ）
- 呼び名に禁止語の一覧（悪口・差別語・性的な言葉など。`src/data/ng-words.ts`）を当て、当たれば作るときに止める。漢字の言葉は、ひらがなに直さずに比べるので別に持つ（「死ね」「馬鹿」など）。短い悪口（でぶ・ぶす・ばか・あほ・くそ）は、名前の前か後ろに付いていても止める（「デブ田中」「クソ田中」など）。名前やあだ名になりうるもの（かす・くず・ちび・ぶた・はげ・ごみ・きも・うざ）は付いていても止めない
  - 比べる前に、全角を半角に・カタカナをひらがなにそろえ、英字に見えるほかの文字（キリル文字の с・і、ギリシャ文字の ο、小さな大文字の ꜱ など）を英字に直し、記号の付いた英字（ü・é）は記号を外し、**ひらがな・漢字・英字・数字以外の文字（記号・空白・長音など）をすべて外す**（「し★ね」「し!ね」のように、決めた区切り文字以外をはさんでもすり抜けられないように）。「は゛か」のような離れた濁点は合成してから比べる
  - 英字の語（shit・fuck など）は、英字のつながりの始まりか終わりにあるときだけ当てる（「Yoshitaka」のようなローマ字の名前を止めないため）
  - 英字とかな・漢字がまざっているときは、英字を外したもの（「しxね」→「しね」）と、1 文字だけの英字をかなに読みかえたもの（「ちnこ」→「ちんこ」。n・a・i・u・e・o）でも確かめる
  - 禁止語を含むが名前として普通に使われる言葉（シンデレラ・ころすけ・あほうどり・バカボン など。`NG_ALLOW`）は、確かめる前に取り除く
- 呼び名（12 文字）と問い合わせ（本文 2,000 文字など）の長さは、見た目の文字数（書記素）のほかに、**文字コードの数でも上限を置く**（見た目の 1 文字につき 16 個まで）。結合文字（濁点など）を重ねると、見た目は 12 文字のまま何万文字にもでき、保存や画像の描画に負担をかけられるため
- 呼び名から、見えない文字と文字の向きを変える文字（U+200B・U+202E など）を取り除く。禁止語のあいだに挟んで確かめをすり抜けたり、表示の順番を入れかえて別の文に見せたりできるため。絵文字をつなぐ U+200D は残し、禁止語を確かめるときだけ外す
- 公開リンク（S7）は検索エンジンに載せない（`noindex`）
- `http://` で来たら `https://` へ移し（`worker.ts`・`src/lib/guard.ts`）、`Strict-Transport-Security` を返す
- よそのサイトから送られてきた API への書き込み（POST など）は断る。`Sec-Fetch-Site` があれば、通すのは `same-origin`（同じサイトのページから）と `none`（どのページからでもない）だけで、`same-site`・`cross-site` は 403。ないとき（古いブラウザ）は `Origin` の名前を比べ、どちらもない（ブラウザではない）呼び出しは通す
- 本文のある API への書き込みは `Content-Type: application/json` だけを受け、ほかは 415 で断る（`src/lib/guard.ts`。API の側の `readJson` も JSON と名乗らない本文を読まない）。よそのサイトのフォームや、下準備の問い合わせ（preflight）なしで送れる形（`text/plain` など）では送れないようにするため。本文のない書き込み（出る・消すなど）と、Stripe からの知らせ（`/api/stripe/webhook`）は除く。定時処理（`/api/cron/cleanup`）は読み取り（GET）なので当たらない
- `Content-Security-Policy` で、よそのサイトのスクリプト・通信・埋め込みを許さない。ほかに `X-Frame-Options: DENY`・`X-Content-Type-Options: nosniff`・`Permissions-Policy` を返す
  - `script-src` の `'unsafe-inline'` は外さない。Next.js はページの中に小さなスクリプト（画面の中身を渡す `self.__next_f.push(…)` など）を直接書く。これを nonce で許すには、通信ごとに nonce を作って描く（すべてのページを動的に描く）必要があり、前もって作っておいたページ（トップ・説明のページなど）を、OpenNext のとっておいた結果から返せなくなる。ハッシュ値で許す方法（`experimental.sri`）は外から読むスクリプトにしか効かず、ページの中に書くスクリプトは許せない。代わりに、呼び名などは必ず文字として扱い、HTML として解釈しない（上記）
- 運営者の合言葉（`ADMIN_TOKEN`）と定時処理の合言葉（`CRON_SECRET`）は、かかる時間から中身が分からない比べ方をする。どちらも、まちがいが同じ IP アドレスから 10 回続いたら 1 時間止め、その間は正しい合言葉でも通さない（運営者は `admin-failure`、定時処理は `cron-failure` として別に数える）。`CRON_SECRET` は 32 文字以上の乱数にする。短いときは、いま動いている設定を止めないよう断らずに、記録（Workers Logs）に注意を残す
- 運営者のページ（`/admin`）には、パスキー（指紋・顔認証。WebAuthn）でも入れる。最初は合言葉で入り、その端末のパスキーを登録する。合言葉は端末をなくしたときの予備として残す
  - 合言葉で入るときは、画面が合言葉を一度だけ `/api/admin/login/token` に送り、パスキーと同じ cookie に替える。合言葉はブラウザのどこ（`sessionStorage` など）にも残さない（ページに入り込んだスクリプトに読まれないように）。前の版が残した `sessionStorage` の値は消す。画面を使わない呼び出しは、これまでどおり `X-Admin-Token` 見出しでも入れる
  - サーバーが持つのは公開鍵だけ（`admin_passkeys`）。指紋や顔のデータは端末の外に出ない。本人の確認（指紋・顔など）を毎回求める（`userVerification: required`）
  - パスキーはドメインごとに登録する（`takoshin.daigakunote.com` で登録したものは、workers.dev では使えない）
  - 登録・確かめの乱数は 1 回だけ使え、5 分で切れる（`admin_challenges`）
  - パスキーか合言葉で入ると、12 時間使える鍵を cookie で渡す（`httpOnly`・`SameSite=Strict`・`/api/admin` だけ）。データベースには鍵のハッシュ値だけを持つ（`admin_sessions`）。「出る」で消す。「すべての端末から出る」（`/api/admin/logout/all`）で、すべての鍵を消せる
  - パスキーの登録と取り外しは、cookie で入っていても、**そのたびに合言葉**（`X-Admin-Token`）を求める。cookie を盗まれても、その cookie だけで自分のパスキーを足して居座ったり、運営者のパスキーを外して締め出したりできないように。まちがいは合言葉のまちがいとして数える
  - パスキーを外すと、すべての端末から出る（どの鍵がどのパスキーで入ったかは持っていないので、外したパスキーで入っていた端末も確実に出すため）
  - パスキーのまちがいも、合言葉のまちがいと同じく数えて止める。何も送っていない（まだ入っていない）ときは数えない
- 招待リンク・公開リンクの ID は、形（URL に使える文字で 16〜64 文字）がちがえば、データベースに問い合わせる前に断る
- 年齢：13 歳未満は保護者と使うよう利用規約に書く

## 11. 技術

### 11.1 構成

| 部分               | 選ぶもの                              | 理由                                                                 |
| ------------------ | ------------------------------------- | -------------------------------------------------------------------- |
| 画面とサーバー処理 | Next.js（App Router）＋ TypeScript    | 1 つの仕組みで画面と API が作れる。結果画像を作る仕組みもある        |
| データベース       | PostgreSQL（Neon・Supabase など）     | §5.3 の「N 人目まで」を、データベースの行の鍵で確実に守れる          |
| 置き場所           | Cloudflare Workers（OpenNext で変換） | 世界中の拠点で動き、無料の範囲が広い。定時処理（Cron Trigger）もある |
| 結果画像           | `next/og`（Satori）                   | サーバーで画像を作れる                                               |

Workers では通信の部品をリクエストをまたいで使い回せないので、データベースには問い合わせごとに接続する。接続を速くするため Cloudflare の Hyperdrive を通す（結果のキャッシュは切る。回答数・状態が古く見えないように）。Worker は Smart Placement でデータベースの近くに置く。
開発とテストでは、PostgreSQL がなくても動くよう PGlite（組み込みの PostgreSQL）を使う。

公開の前に作れるページ（トップ・作る画面・16 タイプの紹介・規約など。`next build` で ○ のもの）は、作ったものを Workers の静的ファイルの置き場から返す（OpenNext の `staticAssetsIncrementalCache`。公開のときに `opennextjs-cloudflare populateCache remote` で写す）。毎回作り直すと最初の応答に 0.3〜1.8 秒かかっていたため。あとから作り直す設定（`revalidate`）は使わない（この置き場は読むだけなので）。

ブラウザから直接データベースに触らせない。読み書きはすべてサーバーの API を通す。

公開するアドレスは `https://takoshin.daigakunote.com`（Workers の独自ドメイン）。`workers.dev` のアドレスもそのまま使える。
転送（リダイレクト）はしない。端末に保存するもの（§8.3）はアドレスごとに分かれるため、転送すると、それまでのアドレスで作った診断の一覧が見えなくなるため。
ただし、人に送るリンク（招待リンク・公開リンク・結果のシェア）は、どちらのアドレスで開いていても `NEXT_PUBLIC_SITE_URL`（独自ドメイン）で作る。診断はデータベースにあるので、どちらのアドレスでも開ける。管理用のリンクは、端末の一覧と合わせるため、いま開いているアドレスのまま。

### 11.2 データの形

```sql
-- 診断
create table surveys (
  id               text primary key,        -- surveyId（招待リンク）
  host_key_hash    text not null unique,    -- hostKey の SHA-256
  nickname         text not null,           -- 1〜12 文字
  target_count     smallint not null check (target_count between 3 and 30),
  response_count   smallint not null default 0,
  status           text not null default 'open'
                   check (status in ('open','completed','expired')),
  self_answers     smallint[] null,         -- 32 個。1〜7、−1 は出していない問（§3.5）
  extended         boolean not null default false,
  expires_at       timestamptz not null,    -- 受付の期限
  completed_at     timestamptz null,
  delete_at        timestamptz null,        -- この時刻に物理削除
  result           jsonb null,              -- 確定した結果（§11.5）
  share_id         text null unique,        -- 公開リンク。公開していなければ null
  question_version smallint not null default 1,
  created_at       timestamptz not null default now()
);

-- 回答
create table responses (
  id             bigint generated always as identity primary key,
  survey_id      text not null references surveys(id) on delete cascade,
  respondent_key text not null,            -- 端末ごとの乱数
  answers        smallint[] not null,      -- 32 個。1〜7、0 は「わからない」、−1 は出していない問（§3.5）
  relation       text null,
  created_at     timestamptz not null default now(),
  unique (survey_id, respondent_key)
);
```

上は中心の 2 つの表だけを示す。あとから足した列（`premium_at`・`gift_at`・`fortune_code`・`support_record_id`）と、ほかの表（`inquiries`・`visit_counts`・`payments`・`support_records`・`admin_passkeys`・`admin_challenges`・`admin_sessions`・`push_keys`・`push_subscriptions`）を含む全体は `src/lib/schema.ts` を正とする。

**N 人目までを確実に守る方法**：回答の保存は 1 つのトランザクションで、

1. `select ... from surveys where id = $1 for update`（その診断の行を他の処理から一時的に止める）
2. 状態が `open` で、`response_count < target_count` かを確かめる。だめなら「締め切り」を返す
3. `responses` に追加し、`response_count` を 1 増やす
4. 増やした結果が `target_count` と等しければ、そのトランザクションの中で §6・§7 の結果を計算して `result` に入れ、`status = 'completed'`・`completed_at`・`delete_at` を入れる
5. 確定する

これで、同時に何人送っても N 人を超えず、結果は N 人分のデータだけで 1 回計算される。

期限切れ・削除は 1 日 1 回の定時処理（Cloudflare の Cron Trigger）で行う（`expires_at` を過ぎた `open` を `expired` に、`delete_at` を過ぎたものを削除）。

### 11.6 性能の目標

- 質問画面：最初の表示 2.5 秒以内（4G 回線のスマホ）。次の問への切り替えは通信しない（32 問を最初に読み込み、深掘りの判断も端末の中で行う）

- 同時に多くの人が開いても動くこと（拡散を考え、1 診断に 1 分で 30 回答が来ても正しく N 人で締め切れること）

- データベースの復元：Neon の復元できる期間（履歴の保存期間）は、契約のプランで決まる。Neon の管理画面で確かめ、必要なら期間を延ばす

### 11.10 「全員そろった」の通知

- 標準の Web Push（RFC 8030）を使う。中身は端末ごとの鍵で暗号化し（RFC 8291 の aes128gcm）、送る側の署名（RFC 8292 の VAPID）を付ける。外部の部品は使わず、Web Crypto だけで組む（Cloudflare Workers でも動くように）。暗号化は RFC 8291 の付録の例と同じ結果になることを試験で確かめる
- 送るための鍵（VAPID）は、初めて使うときに作ってデータベース（`push_keys`）に置く。設定するシークレットを増やさないため
- 送り先（`push_subscriptions`：診断の ID・送り先のアドレス・端末の公開鍵）は診断ごとに持ち、N 人目の回答で結果が確定したら通知を送って消す（1 回きり）。診断を消すといっしょに消える。送り先のアドレスは、ブラウザの通知の中継の会社（Google・Mozilla・Apple・Microsoft）のものだけを受け付ける（このサーバーから任意の相手へ送らされないため）
- 通知の中身：「そろった！」「たこ診の診断に全員が答えました。結果を見てみよう」と診断の ID。ロック画面に出るので、呼び名は入れない。管理用の鍵はサーバーにないので入れない。押すと `/?open={surveyId}` を開き、端末に覚えてある鍵でその診断を開く（§4.2）
- 通知は返事を返したあとに送り（Cloudflare では `waitUntil`）、最後の回答者を待たせない。届かなくても回答の受付には響かせない（結果は S5 とトップで見られる）
- 受け取るのは `public/sw.js`（通知を出して、押されたら開くだけ。ページの読み込みには手を出さない）。登録するのは、本人が「通知を受け取る」を押したときだけ
- iPhone・iPad は iOS 16.4 以降で、ホーム画面に追加したアプリの中でだけ通知を受け取れる。そのためアプリの情報（`manifest`）の表示の形を `standalone` にする。ホーム画面のアプリは Safari と保存場所が分かれているので、管理用リンクを貼り付けて開いてもらう（§4.2・§4.6）

### 11.11 流入から診断の完成までの計測

目的：「人が来ない」「回答が集まらない」「結果から広がらない」を見分ける。主な指標は「テストを除いた、週ごとの完成した診断の数」（完成した週で数える）。アクセス数や共有のボタンを押した数だけを成功の指標にしない。外部の解析サービスは使わない。

**出来事**（どれも件数で、同じ人の重複を含む。登録なしでは人を見分けられないので「人数」とは言わない）

| 出来事                                   | 数えるところ                                                  | 内訳                                                                                        | 二重に数えない仕組み                                                  |
| ---------------------------------------- | ------------------------------------------------------------- | ------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| 作成画面の表示 `create_view`             | 画面                                                          | 流入元                                                                                      | ―                                                                     |
| 診断の作成 `created`                     | サーバー（作成と同じトランザクション）                        | 流入元                                                                                      | 作れたときだけ                                                        |
| 招待の操作 `invite`                      | 画面                                                          | `line`・`copy_text`・`copy_link`・`share`・`qr`                                             | ―（押した回数。実際に送ったかは分からないので、送ったとは記録しない） |
| 回答の開始 `answer_start`                | 画面                                                          | その招待リンクを開いたときの送り方（`?from=` かアプリ内ブラウザー。作った人の流入元とは別） | 同じ端末・同じ診断で 1 回だけ                                         |
| 回答にかかった時間 `answer_time`         | 画面（受け付けられたあと）                                    | 3 分未満・3〜6 分・6〜10 分・10 分以上                                                      | 受け付けられたときだけ                                                |
| 回答の受け付け `response`                | サーバー（受け付けと同じトランザクション。`stats_responses`） | その招待リンクの送り方                                                                      | 二重の回答は受け付けないので数えない                                  |
| 診断の完成 `completed`                   | サーバー（結果の確定と同じトランザクション）                  | 流入元                                                                                      | 診断ごとに最初の 1 回（人数をふやして出し直した結果は数えない）       |
| 結果の表示 `result_view`                 | サーバー（結果の画面から知らせる）                            | 流入元                                                                                      | 診断ごとに最初の 1 回                                                 |
| 画像の保存・共有の操作 `image`           | 画面（共有の画面を開いた・ダウンロードした）                  | 縦・横 × 共有の画面・ダウンロード                                                           | ―（投稿したかは分からない）                                           |
| 結果を X・LINE で送る操作 `result_share` | 画面                                                          | `x`・`line`                                                                                 | ―（押した回数）                                                       |
| 公開リンクの作成 `public_created`        | サーバー                                                      | 流入元                                                                                      | 診断ごとに最初の 1 回                                                 |
| 公開カードの表示                         | 「リンクが開かれた回数」（§8.1）の `public`                   | 送り方                                                                                      | ―                                                                     |
| 回答完了の画面・公開カードからの作成     | 作成画面の `?entry=` を診断ごとの記録に残す                   | ―                                                                                           | ―                                                                     |

**流入元**：`line`・`instagram`・`tiktok`・`x`・`qr`・`copy`・`share`・`search`・`other`・`none`（直接／不明）の決まった値だけ。端末の中で、アドレスの目印（`?from=`・`?utm_source=`）→ アプリ内ブラウザーの種類 → 前のページのアドレスの順に決め、7 日間覚える。投稿ごとに比べるときは、`src/data/funnel.ts` の `CAMPAIGNS` に足したキャンペーンの目印（`?c=`）だけを記録する。

**データ**

- 作成・完成・結果の表示・公開リンクの作成は `survey_stats` の日時から、回答の受け付けは `stats_responses`（診断ごとの記録ごと・日・送り方の件数）から数える。あとからテストとして外したとき、すべての表から外れるように
- `funnel_counts`：画面での操作の、日（日本時間）・出来事・内訳・テストかどうかごとの件数だけ。画面からは `/api/event` に出来事と内訳だけを送る（決まった値以外は記録しない。同じ回線から出来事ごとに 1 時間 60 件まで）
- `survey_stats`：診断ごとに 1 行。作った日時・流入元・キャンペーン・入口・テストかどうか・人数と、最初の回答・完成・結果の表示・公開リンクの作成の日時。行の ID は診断の ID とは別の乱数で、診断からだけたどれる（`surveys.stats_id`）。呼び名・回答・管理用の鍵・診断の ID は入れない。診断を消すと、どの診断の記録かは分からなくなり、件数としてだけ残る
- どちらも 400 日で消す（1 日 1 回の定時処理）。プライバシーポリシーに書く

**テストの除外**：運営者のページで「この端末をテスト用にする」と、その端末で作った診断と操作に印が付く。作ってしまった診断は、招待リンクを貼り付けて外せる（作成・回答・完成などの件数もすべて外れる）。ただし、ほかの人の端末での画面の操作（回答の開始など）は、どの診断の操作かを残さないので外せない。集計はテストを除いて出し、「テストも含める」を選んだときだけ含める。

**運営者のページ**（集計だけを出す）

- 主な指標：週ごとの完成した診断の数（最近 8 週）
- 週ごとの出来事の件数
- 作った週ごとの完成率：作成・24 時間以内・7 日以内に完成した割合（分母は、作ってから 24 時間・7 日たった診断だけ）・最初の回答までの時間（中央値）・3 人で作った数。はじめの人数を変えた前後を比べるため
- 入口ごと・流入元ごと・キャンペーンごと：作成・7 日以内に完成した割合・完成した数
- 最近 30 日の、出来事ごとの内訳

計測はこの仕組みを入れた日からで、それより前の診断は入らない。比べるときは経過時間をそろえ、少ない件数の数ポイントの差だけで決めない。複数の変更を同じ日に入れたときは、それぞれの効果は切り分けられない。

### 11.12 問ごとの質

測る道具として問がうまく働いているかを、データがたまったら運営者のページで確かめる（`/api/admin/items`）。最近 90 日の、テストを除いた、今の版の問の回答だけを使い、まとめた数字だけを出す（だれの・どの診断の答えかは出さない）。

- 基本の 16 問（だれにも出る問）だけを見る。深掘りの問は半々に近い人にだけ出るので、そのままでは比べられない
- 軸ごとのまとまり（クロンバックの α）：4 問とも 1〜7 で答えた回答で、左の極の向きにそろえた点（右の極の問は 8 − 答え）から出す。0.7 前後あれば目安を満たす
- 問ごとの「ほかの問との相関」：その問と、同じ軸のほかの 3 問の合計点の相関。0.3 未満やマイナスの問は、言い方を見直す候補
- 問ごとの「わからない」の割合と、向きをそろえた点の平均
- 回答が 30 件に届くまでは値を出さない（数字がぶれるため）

## 12. 16 タイプの本文

各タイプ：**友達から見たあなた**／**強み**（3）／**ちょっと気をつけたいところ**（2）／**友達のあるある**（3）／**相性**（ラク・刺激）。

### 考察界隈

- **あるある**：「その服どこの？（毎回聞かれる）」／「写真のセンスがプロ」／「怒るより先にスッといなくなる」
- **相性**：ラク＝ESFJ、刺激＝ESTJ

#### ESTP 切り込み隊長

- **友達から見たあなた**：考えるより先に、もう体が動いている人。「とりあえず行ってみよう！」が口ぐせで、この人と一緒だと退屈する暇がありません。行き当たりばったりで入ったお店が大当たりだった、という思い出をくれるのもこの人。度胸があって、初めての場所や人にも物おじしません。トラブルが起きても、その場の判断で何とかしてしまう頼もしさもあります。細かい計画は苦手でも、いざというときの瞬発力はピカイチ。みんなを外の世界に連れ出してくれる、エネルギッシュな存在です。この人がいると、何でもない一日がちょっとした冒険になります。
- **強み**：行動力（迷っているあいだに、もう一歩を踏み出せます。）／対応力（予想外のことが起きても、その場で最善の手を打てます。）／交渉力（相手や空気を読んで、話をうまくまとめられます。）
- **気をつけたいところ**：勢いで決めて、あとで「やっぱり無理だった」となることも。大きな買い物や約束の前は、一晩おいてみると安心です。／退屈な作業を後回しにしがち。つまらないことほど先に片づけると、あとの楽しみが増えます。
- **あるある**：「今から行ける人ー！」／「ノープランが一番楽しい」／「ピンチのときだけ急に頼れる」
- **相性**：ラク＝ISTJ、刺激＝ISFJ

#### ESFP アイドル

- **友達から見たあなた**：その場にいるだけで、空気がパッと明るくなる人。ノリがよくて、楽しいことを見つける天才です。誰とでもすぐ打ち解けて、初対面の人ともいつの間にか仲良くなっています。人を笑わせたり楽しませたりするのが好きで、写真や動画を撮るときもいつも中心に。みんなが疲れて静かになった帰り道でも、この人の一言でまた笑いが起きます。落ち込んでいる人がいると、明るさで元気づけてくれる優しさも持っています。「今」を全力で生きている姿が、周りを元気にしているのです。この人のいない集まりは、どこか物足りなく感じられます。
- **強み**：盛り上げ力（どんな場でも、楽しい空気をすぐに作れます。）／親しみやすさ（初めての相手とも、壁を感じさせずに仲良くなれます。）／表現力（うれしい・楽しいを素直に伝えて、周りを笑顔にできます。）
- **気をつけたいところ**：楽しいことを優先して、面倒なことがたまりがち。「楽しみの前に 10 分だけ片づけ」を習慣にすると最強です。／真剣な話を、つい笑いではぐらかしてしまうことも。大事な場面では、少しだけ笑いを置いて聞いてみてください。
- **あるある**：「え、楽しそう！行く！」／「この人のストーリー見ると元気出る」／「気づいたら知らない人と友達になってる」
- **相性**：ラク＝ISFJ、刺激＝ISTJ
  > 相性の決め方：「ラク」は 4 文字のうち 2 文字目（S/N）と 3 文字目（T/F）が同じで、1 文字目（E/I）と 4 文字目（J/P）が逆のタイプ、
  > 「刺激」は 2 文字目だけが同じで、ほかの 3 文字が逆のタイプとした。考え方の土台（ものの見方）が同じで、行動の向きが補い合う組み合わせ、という遊びの決まりである（§7.8 のとおり根拠はない）。
  > この決まりでは、どのタイプも 2 つの相手がちょうど 1 つずつ決まり、相手から見ても同じ関係になる（A のラクが B なら B のラクも A）。

## 17. 将来の案（実装する予定。まだ作っていない）

### 17.1 友達どうしで、いつでも答えられる

お互いに友達になった人どうしは、人数の設定に関係なく、いつでも相手について答えられるようにする。

**守ること（§8.5 と同じ考え方）**

- 答えはいつでも受け付けるが、結果を出し直すのは、新しい答えが 3 人分たまったときだけにする。1 人ずつ出し直すと、前後の結果の差から、いま答えた人の答えが分かってしまうため（§5.4 で、結果のあとに人数をふやすときは 3 人以上としているのと同じ理由）
- だれが答えたかは出さない（「○○さんが答えてくれました」のような知らせもしない）
- 友達が少ないと、3 人分ずつの反映でも、だれのことか見当がつきやすい。反映の単位を 3 人より大きくすることも、作るときに決める
- ホストが別人として友達になると、ほかの人の答えをしぼり込める（§8.4）。結果を出し直すたびにくり返し使えてしまうため、友達の数の下限や、反映の単位で弱める方法を、作るときに決める

**作る必要があるもの**

| -------------------- | -------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| 本人を見分ける仕組み | ない（ホストは管理用リンクだけ。§16 の「会員登録・ログイン」） | 友達関係を続けて持つための「自分のページ」と、その鍵（パスキーなど）                      |

### 17.2 友達のタイプ帳（17.1 とつなげる案）

- Instagram の相互フォローから、友達の結果を集めることはできない。Instagram が外部のアプリに開いている API では、フォローしている人の一覧が取れないため（個人アカウント向けの Basic Display API は 2024 年 12 月に終わり、いまの API でも数しか取れない。作るときに Meta の最新の開発者向けの説明で確かめる）。画面から抜き出す方法は Instagram の規約に反するので使わない
- 代わりに、シェアされたカード（`/r/…`）を開いたときに「友達のタイプ帳に入れる」で自分の端末に残す。本人がシェアを選んだカードだけなので、同意の問題がない
- 17.1 の友達の仕組みができたら、お互いに承認した人どうしでタイプを見せ合えるようにする
- 呼び名は「16 タイプ」のままにする（「MBTI」は商標のため）
